# nextjs-supabase-template

Шаблон проекта с готовой архитектурой, правилами и проверками: Next.js 16 (App Router, Cache Components, React Compiler), Supabase (Auth, Postgres с RLS), строгий TypeScript (`@tsconfig/strictest`), shadcn/ui, next-safe-action + react-hook-form + Zod, nuqs, Intl-форматы денег и дат с часовым поясом проекта, ESLint 10 с проверкой архитектурных границ, Prettier, knip, jscpd, Vitest + Testing Library, Playwright (e2e и замер скорости страниц), pgTAP, lint-staged, GitHub Actions и настройки Claude Code с плагином `dev-kit`. С первого коммита весь пайплайн зелёный.

## Новый проект из шаблона

```bash
gh repo create <org>/<проект> --template Volodymyr-FullStack-Pro/nextjs-supabase-template --private --clone
cd <проект>
fnm use                      # Node 24 из .nvmrc (или nvm use)
npm ci                       # ставит зависимости и git-хуки
npx playwright install       # браузеры для e2e и замера скорости
cp .env.example .env.local   # локально — адрес и ключи из `supabase status`; облако — Supabase → Project Settings → API
supabase start               # локальный Supabase (Supabase CLI той версии, что в .github/workflows/db.yml, и Docker)
npm run seed:test-user       # тестовый пользователь по .env.test.local или переменным окружения (TEST_USER_*), код второго фактора — npm run totp -s
npm run dev
```

Репозиторий в организации заказчика, у которой нет доступа к шаблону: заказчик создаёт пустой приватный репозиторий, разработчик переносит шаблон без истории — руководство по системе разработки (`claude-kit/docs/GUIDE.md`), раздел «Проект в организации заказчика», п. 2; дальше — блок `B00-setup`.

Затем: заменить `<Проект>` в `CLAUDE.md` и `docs/`, записать первое решение в `docs/knowledge/decisions.md`, первый модуль `npm run new:module <модуль> <запись>` — после разбиения ТЗ на блоки, при работе с ClickUp переименовать `.claude/rules/clickup.md.example` в `clickup.md`.

Безопасность: в Supabase выключить саморегистрацию (Authentication → «Allow new users to sign up» = off; пользователи заводятся приглашением), а если приложение закрыто Cloudflare Access — проверять его JWT в `proxy.ts` или закрыть `*.vercel.app`, иначе периметр обходится (`.claude/rules/auth.md`, `security.md`). В репозитории включить оповещения Dependabot и автоматические security-PR (`gh api -X PUT repos/<org>/<проект>/vulnerability-alerts` и `.../automated-security-fixes`), защитить `main` (PR и зелёный CI обязательны). Версия Supabase CLI в `.github/workflows/db.yml` закреплена и должна совпадать с `supabase --version` на машинах разработчиков: обновлять обе вместе.

Второй фактор и журнал изменений уже в шаблоне. Вход по паролю дополняется кодом из приложения-аутентификатора (TOTP): экраны `/mfa/setup` и `/mfa/verify` в модуле `auth`; у кого фактор подключён, тот после пароля попадает на `/mfa/verify`, а с `AUTH_REQUIRE_MFA=true` (финансовые проекты) без фактора — на `/mfa/setup`. Проверяют пять мест: `src/proxy.ts` (редирект, для `/api/*` — отказ 401 или 403), `requireVerifiedSession()` на страницах за входом (редирект, если запрос обошёл proxy), `verifiedSessionOrResponse()` в Route Handlers (401 или 403 без редиректа), `authActionClient` (Server Action отказывает) и база — ограничивающая политика `private.mfa_ok()` на каждой таблице: с подтверждённым фактором строки видны только в сессии `aal2`. В production второй фактор обязателен по умолчанию (`AUTH_REQUIRE_MFA` не задана = `true`), неудачные входы и неверные коды попадают в лог и в Sentry событием `auth-failure`. Журнал `audit.log` (схема `audit`, закрыта для API) пишет триггер `audit.record()`: кто, когда, операция, старая и новая строка. Новая таблица получает ту же политику и тот же триггер (образец — миграции `*_second_factor_policies.sql` и `*_audit_log.sql`). Цена: в сессии `aal1` проверка фактора — запрос к Supabase Auth (`listFactors`) в `proxy.ts` и в `verifySession`; в `aal2` запросов нет.

Для `/notes`, `npm run gate`, `npm run db:types`, pgTAP и e2e за входом (`npm run test:e2e:db`) нужны Docker и Supabase CLI (`brew install supabase/tap/supabase`). Тестового пользователя заводит `npm run seed:test-user` по `.env.test.local` или переменным окружения `TEST_USER_*`, файл не обязателен; код второго фактора — `npm run totp -s` из тех же источников.

Хостинг и выпуск — [docs/release.md](docs/release.md): Vercel в регионе Франкфурт (`fra1` в `vercel.json`), Supabase в регионе Frankfurt, миграции и настройки Auth на staging и production выкладывает `deploy-db.yml`, ошибки сервера — Sentry (`src/instrumentation.ts`, организация в регионе EU).

## Архитектура: модули и четыре слоя

Код разложен по доменам (модулям), внутри модуля — по слоям. Правило одно: зависимости направлены внутрь, к чистому ядру; фреймворки и база — снаружи и заменяемы. Нарушение правила — ошибка `npm run lint`, а не замечание на ревью.

### Что это за архитектура

Это **модульный монолит**: одно приложение, одна база и один деплой, а внутри — независимые модули с проверяемыми границами. Каждый модуль устроен по **чистой архитектуре** (порты и адаптеры): в центре правила, снаружи база и фреймворк. Подход собран из проверенных практик, а не придуман заново:

| Откуда                              | Что взяли                                                                                                                                         |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Domain-Driven Design                | модуль — предметная область целиком (ограниченный контекст): бизнесы, инвестиции, обязательства; у каждой свои данные, правила, сценарии и экраны |
| Чистая и гексагональная архитектура | слои `domain` → `application` → `infrastructure` и `ui`, зависимости только внутрь; база подключается через порт (интерфейс), а не напрямую       |
| Вертикальные срезы                  | всё по одной области лежит в одной папке, а не разбросано по общим папкам «контроллеры», «сервисы», «модели»                                      |
| Модульный монолит                   | модули живут в одном приложении и не лезут друг другу во внутренности; когда понадобится, модуль выносится в отдельный сервис                     |

Чем это не является: не Feature-Sliced Design (там слои общие на всё приложение, а фича — одно действие пользователя; модуль здесь ближе к модулю Angular или NestJS), не MVC с папками по типу файлов и не микросервисы с первого дня (они дороги в разработке и эксплуатации, пока нагрузка и команда этого не требуют).

### Папки

```
src/app/                         тонкие page/layout: только композиция и Suspense, никакой логики
src/modules/<домен>/
  domain/                        модели (Zod), чистые правила, ошибки домена. Без React, Next, Supabase
  application/                   use cases и интерфейсы репозиториев (порты)
  infrastructure/                реализации портов: Supabase, внешние API; *.fake.ts — для тестов
  ui/                            actions (next-safe-action → use case), формы, компоненты, search-params
  server.ts                      точка сборки: use cases с реальными репозиториями (единственный «DI»)
src/shared/
  domain/                        деньги (decimal.js), Result, ошибки домена, текст, даты и часовой пояс
  infrastructure/                клиенты Supabase (сессия пользователя, секретный ключ), типы базы, env
  lib/                           safe-action (actionClient, mfaActionClient, authActionClient, fail), session, cron, runtime
  ui/                            shadcn/ui, form/TextField, SubmitButton, sonner
src/proxy.ts                     обновление сессии и редиректы (не единственная защита)
```

Простыми словами, на примере модуля `businesses`:

| Папка                       | Что это                                                                                        | Пример                                                                                                           |
| --------------------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `src/app`                   | адреса страниц: какой экран открывается по какому URL; сами ничего не считают и не читают базу | `src/app/businesses/page.tsx` показывает список бизнесов                                                         |
| `domain`                    | что такое запись и какие у неё правила; чистый TypeScript без базы, React и Next               | схема бизнеса: доля от 0 до 100 %, оценка не меньше нуля; ошибка «доля больше 100 %»                             |
| `application`               | что с записью можно делать (сценарии) и что для этого нужно от хранилища (порт)                | `create-business.ts`, `list-businesses.ts`; `businesses-repository.ts` — «сохранить, найти, список» без Supabase |
| `infrastructure`            | как это хранится и откуда приходит                                                             | `businesses-repository.supabase.ts` — запросы к базе; `businesses-repository.fake.ts` — хранилище для тестов     |
| `ui`                        | как это выглядит и как отправляется                                                            | форма, список, action сохранения, параметры поиска в URL                                                         |
| `server.ts`                 | сборка модуля: сценарии с настоящей базой; через него модуль видят страницы и другие модули    | `businesses.list(...)`, `businesses.create(...)`                                                                 |
| `src/shared/domain`         | общие правила для всех модулей                                                                 | деньги, `Result`, ошибки, нормализация текста, даты                                                              |
| `src/shared/infrastructure` | общие подключения                                                                              | клиенты Supabase, типы базы, переменные окружения                                                                |
| `src/shared/lib`            | общая техника Next.js                                                                          | безопасные actions, сессия                                                                                       |
| `src/shared/ui`             | общие элементы интерфейса                                                                      | кнопки, поля, карточки shadcn                                                                                    |
| `src/proxy.ts`              | входная дверь: выполняется до любой страницы                                                   | обновляет сессию и отправляет незалогиненных на вход                                                             |

Кто куда может обращаться:

| Слой             | Что в нём                 | Может импортировать                                                                                                           |
| ---------------- | ------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `domain`         | модели, правила, ошибки   | свой `domain`, `shared/domain`, пакеты без I/O (zod, decimal.js)                                                              |
| `application`    | use cases, порты          | свой `domain` и `application`, `shared/domain`                                                                                |
| `infrastructure` | репозитории, шлюзы, фейки | свой `application` и `domain`, `shared/domain`, `shared/infrastructure`                                                       |
| `server.ts`      | сборка                    | свой `application`, `infrastructure`, `domain`, `shared/*` кроме `ui`                                                         |
| `ui`             | actions, компоненты       | свой `server.ts`, `domain`, `ui`; `shared/ui`, `shared/lib`, `shared/domain`; чужие модули — только их `server.ts` и `domain` |
| `app`            | маршруты                  | `modules/*/ui`, `modules/*/server.ts`, `modules/*/domain`, `shared/ui`, `shared/lib`, `shared/domain`                         |

`domain` и `application` из пакетов npm могут импортировать только `zod` и `decimal.js` — всё остальное запрещено `eslint-plugin-boundaries` (конфигурация в `eslint.config.mjs`). Тесты живут в `tests/unit`, зеркалом `src`: рядом с кодом они нарушили бы границы. Barrel-файлы (`index.ts` с реэкспортом) не используются: импорт по точному пути, это быстрее собирается и лучше анализируется.

**Защиты денег и доступа.** Кроме границ, линтер ловит ошибки, которые дают неверные деньги или открытые данные, — локальные правила `local/*` в `eslint.config.mjs`: сумма числом и операторы на `Money`; превращение строк в числа и чтение часов в ядре; Server Action мимо `authActionClient` и владелец из входа, а не из сессии; `verifySession` и `actionClient` вне модуля `auth`; свой клиент базы вне `shared/infrastructure`; ответ Supabase без проверки `error` и `select('*')` в репозитории; непроверенный `Result` и `throw` в use case; плановая задача без проверки секрета. Там же: свой клиент actions (пакет `next-safe-action` импортирует только `src/shared/lib/safe-action.ts`), динамический `import()` к `db`, `admin`, пакетам клиента и `session`, ответ PostgREST, прочитанный без проверки `error` (`result.data ?? []`), текст ошибки базы или Auth в исключении (`error.message`, `cause`) вместо операции и кода. Там же после повторного ревью: запись в Supabase с выброшенным ответом и запрос без `await`; путь импорта с `/./` или `/../` и импорт за пределы `src`; `require()`; файл не `.ts`/`.tsx` в `src`; плановая задача в группе маршрутов и в `route.tsx`. Сообщение правила говорит, как исправить. Защиты ловят ошибку — разработчика или ИИ-агента, — а не намеренный обход: правило видит формы кода из своих проб, остальное смотрит ревью кода. Отключить защиту комментарием — ошибка `npm run lint`: `eslint-disable` защиты (`no-restricted-disable`) и комментарий-конфигурация `/* eslint правило: "off" */` (`no-use`). `npm run lint:rules` (входит в `check` и CI) линтует пробы из `tests/lint-rules/fixtures` настоящим конфигом: каждое правило обязано поймать свою пробу и промолчать на хорошем коде, правило без пробы — ошибка; вторым проходом он линтует весь `src` без учёта комментариев ESLint и падает, если защита в коде отключена комментарием вместе с правилами, которые это запрещают. Правку самого `eslint.config.mjs` и проб видит только ревью диффа. Имена правил и то, что остаётся ревью, — `.claude/rules/code-style.md` и `architecture.md`.

### Преимущества

- **У каждой вещи одно место.** Любой модуль устроен одинаково: новый человек разбирается за минуты, ревью короче, Claude Code не выбирает, «куда положить».
- **Правила проверяются за миллисекунды.** Расчёты денег и бизнес-правила — чистые функции в `domain`: тесты идут без базы и браузера, покрытие `domain` — 100 %.
- **Архитектура не расползается.** Границы проверяет линтер на каждом коммите и в CI, а не память людей: через год код устроен так же, как в первый день.
- **Модули не мешают друг другу.** Правка в одном модуле не ломает другой; несколько человек работают параллельно почти без конфликтов в git.
- **Замена без переписывания.** Другая база, внешний сервис или библиотека интерфейса меняют один слой; правила и экраны остаются.
- **Безопасность по умолчанию.** Данные читаются только через сценарий с `userId` и клиент с RLS: чужие строки база не отдаст, даже если в коде ошибка.
- **Скорость не страдает.** Слои — это папки и импорты, а не обёртки во время работы: нет DI-контейнера, рефлексии и лишнего JavaScript в браузере; страницы остаются серверными компонентами с кэшем Next.js.
- **Просто и дёшево в эксплуатации.** Одно приложение и одна база: один деплой, одни логи, обычные транзакции без распределённых протоколов.
- **Рост без переезда.** Нагруженный модуль выносится в отдельный сервис, не задевая остальные (см. «От лендинга до высоконагруженной системы»).

**Цена.** На старте файлов больше, чем в «одной папке с компонентами»: на одну запись — модель, сценарий, порт, репозиторий, фейк и тесты. Каркас создаёт генератор, поэтому это минуты, а не часы. Страницам без данных (лендинг) слои не нужны вовсе: там работают только `src/app` и `shared/ui`.

### Как проходит запрос

1. **Чтение.** `page.tsx` рендерит статическую оболочку и оборачивает динамику в `<Suspense>`. Серверный компонент из `ui/` берёт сессию через `requireVerifiedSession()` (она проверяет и шаг второго фактора; `verifySession` без этой проверки — только модуль `auth`, остальным его запрещает линтер) и вызывает use case из `server.ts`; use case ходит в порт, порт реализован на user-scoped клиенте Supabase (RLS применяется). Наружу уходит модель домена, не строка таблицы.
2. **Запись.** Форма (`useHookFormAction` + Zod-схема из `domain`) вызывает action из `ui/actions.ts`. `authActionClient` проверяет сессию в middleware и валидирует вход той же схемой; action вызывает use case, получает `Result`, при ошибке домена делает `fail(error)` (клиенту уходит код ошибки и правило, не текст), затем обновляет данные: `updateTag(tag)` для кэшированных, `refresh()` для динамических на текущей странице.
3. **Ошибки.** Ожидаемые (`NotFoundError`, `ForbiddenError`, `ConflictError`, `RuleViolationError`) возвращаются из use case как `Result` с кодом (`code`, у правила ещё `rule`); `domain` и `application` текстов для пользователя не содержат, сообщения Zod — тоже ключи. Тексты — в словаре модуля `ui/messages.ts` (`satisfies Record<ключ | код, string>`, неполный словарь — ошибка типов), общие — в `src/shared/ui/form/messages.ts`; форма показывает их через `failureMessage` и `TextField messages={…}`. Язык один — `DEFAULT_LOCALE` (`src/shared/domain/locale.ts`: `lang`, деньги, даты); второй язык — next-intl по тем же ключам. Неожиданные (сеть, база) бросаются и превращаются в общую фразу в `handleServerError`; причина уходит строкой JSON в лог и в Sentry (`src/shared/infrastructure/monitoring.ts`; Sentry включается переменной `SENTRY_DSN`, `docs/release.md`).
4. **Кэш.** Данные пользователя читаются динамически под Suspense. Справочники и редко меняющиеся данные — компоненты и функции с `'use cache'`, `cacheLife`, `cacheTag`; инвалидация — `updateTag(tag)` (или `revalidateTag(tag, 'max')`, в Next 16 второй аргумент обязателен) в action, который их меняет. Внутри `'use cache'` нельзя читать cookies и сессию.

### Новый модуль

```bash
npm run new:module businesses business
```

Как `ng generate` в Angular, только целиком: генератор создаёт полный рабочий срез одной сущности — `src/modules/businesses/{domain,application,infrastructure,ui}` и `server.ts`, форму, список, словарь, action, страницу `src/app/businesses/page.tsx`, миграцию таблицы со всеми обязательными политиками и триггерами, её pgTAP, unit-тесты и e2e (20 файлов, около 1 250 строк) — с полями-заготовкой `title`, `amount`, `currency`. Имя, которое шаблоны объявляют сами (`items`, `result`, `promise`, `session`…), имя из одной буквы и `generator-probes` (его занимает проверка шаблонов) генератор не принимает и говорит почему. После `supabase migration up && npm run db:types` и `npm run budget -- --update-baseline` срез проходит `npm run gate`; дальше поля, правила и тексты меняются под сущность — тремя задачами: база и pgTAP, ядро и unit, экран и e2e (`.claude/rules/docs.md`). Шаблоны лежат в `scripts/module-template/` настоящими файлами с метками вместо имён и служат исполняемым образцом после удаления примера `notes`; что они не устарели, проверяет `npm run generator:check` (`.claude/rules/architecture.md`).

**Модули и чужие данные.** Из `ui` и `app` чужой модуль доступен через его `server.ts` (use cases) и `domain` (типы). Внутри `application` и `infrastructure` чужие use cases не вызываются: агрегирующий модуль (например, портфель, которому нужны бизнесы и инвестиции) описывает свой порт и реализует его своим репозиторием поверх таблиц или представления в базе. Так модули остаются независимыми, а агрегаты считаются там, где данные.

### От лендинга до высоконагруженной системы

Правило зависимостей, слои и тесты одинаковы на любом масштабе; меняется только то, что добавляется вокруг них.

| Масштаб                                | Как устроено                                                                                                                         | Что добавляется                                                                                                                                                                                                                              |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Лендинг, сайт-визитка                  | страницы в `src/app/(marketing)` и компоненты `shared/ui`; модуль — только там, где есть данные (например, `leads` для формы заявки) | статическая отдача и CDN Vercel, `'use cache'`                                                                                                                                                                                               |
| Кабинет, внутренняя система, учёт, CRM | модуль на каждую предметную область; правила — в `domain`, права — RLS и use cases                                                   | плановые задачи `src/app/api/cron/*`, реестр требований, блоки поставки                                                                                                                                                                      |
| SaaS для многих компаний               | плюс модуль `organizations`, колонка `organization_id` и RLS по членству; организация — в контексте use case рядом с `userId`        | роли, тарифы, письма                                                                                                                                                                                                                         |
| Растущая нагрузка                      | те же модули, без перестройки                                                                                                        | кэш с тегами, агрегаты и индексы в базе, пагинация на сервере, реплики чтения Supabase, очередь для долгих задач (Supabase Queues или Trigger.dev)                                                                                           |
| Высокая нагрузка, несколько команд     | модули становятся пакетами монорепозитория, у каждого — своя команда                                                                 | нагруженный модуль выносится в сервис: его `domain` и `application` переезжают без изменений, в приложении остаётся адаптер в `infrastructure`, который ходит в сервис по HTTP или через очередь; страницы и другие модули этого не замечают |

Отдельная служба рядом с приложением нужна для постоянных соединений в реальном времени (Supabase Realtime), тяжёлых вычислений и долгих сценариев с повторами. Основное приложение при этом остаётся модульным монолитом.

## Чистый код

Линтер держит код простым и читаемым, а правила и ревью — осмысленным: без комментариев (смысл в именах, структуре и тестах, причины решений — в журнале `docs/knowledge/decisions.md`; разрешены только директивы инструментов), файл ≤ 300 строк (потолок; единую ответственность держат лимиты на функцию), функция ≤ 80 строк (компонент `.tsx` ≤ 120) и ≤ 3 параметров, сложность ≤ 10, без магических чисел, имена без сокращений и одиночных букв, kebab-case файлов, `eslint-disable` только с именем правила (проверяет линтер) и причиной в той же строке (проверяет линтер: `require-description`); отключение границ слоёв и защит денег и доступа комментарием — ошибка (что и чем проверяется — `.claude/rules/code-style.md`). Принципы DRY (на третьем повторе), KISS, YAGNI, честный TypeScript и неизменяемость — в скиле `dev-kit:code-style`, особенности шаблона — в `.claude/rules/code-style.md`. Компоненты shadcn в `src/shared/ui` — сторонний код: к ним применяются границы импортов и защиты доступа (Server Action, свой клиент базы и actions, `process.env`, запрет отключать защиты), стилевые и строгие типовые правила — нет. Корневые конфиги (`eslint.config.mjs`, `vitest.config.mts` и т. п.) и SQL могут содержать комментарии — правило «без комментариев» действует на `src`, `scripts` и `tests`.

**Типы, ввод, повторы.** `any` запрещён; `unknown` и `as` линтер допускает только там, где данные приходят извне (`infrastructure`, `shared/lib`, `app/api`, `proxy.ts`), и там `as` не сужает тип: данные разбирает Zod. Текст пользователя нормализуется один раз в Zod-схеме `domain` (`normalizeText` из `src/shared/domain/text.ts`: NFC, без невидимых символов, схлопнутые пробелы), поиск — `normalizeSearch` в use case. Импорты сортирует и группирует линтер (`simple-import-sort`, `import/no-duplicates`, `consistent-type-imports`); barrel-файлов нет — короткие импорты даёт `server.ts` модуля. Формы отправляются через `SubmitButton` (блокировка, `aria-busy` и спиннер на время action); операции, которые пользователь может повторить, идемпотентны (`client_request_id`), индексы строятся под запросы списков — скил `dev-kit:supabase-rls`. Базовые заголовки безопасности — в `next.config.ts`.

**Дизайн и качество интерфейса.** Выбор заказчика записывается в `docs/design/design-system.md`, значения — токенами в `src/app/globals.css`; цвет значением в коде ловит линтер. E2E идёт на компьютере (Chrome 1440×900) и на iPhone (Safari); `checkPageQuality` (`tests/e2e/support/page-quality.ts`) проверяет доступность WCAG 2.2 AA (axe) в светлой и тёмной теме, отсутствие горизонтальной прокрутки, в том числе на 320 px, и содержимого, обрезанного контейнером: `tests/e2e/ui-quality.spec.ts` — на каждой странице, сценарий модуля — на странице с данными (сумма из 16 цифр, строка максимальной длины; образец — `tests/e2e/notes-quality.spec.ts`). Порядок «варианты дизайна заказчику → выбор → код» — скил `dev-kit:design-system`.

## Производительность

Бюджет на маршрут: TTFB ≤ 200 мс, LCP ≤ 1,5 с (телефон — 2,5 с), TBT ≤ 200 мс (телефон — 400 мс), CLS ≤ 0,1, оценка по формуле Lighthouse ≥ 0,9, данные страницы приходят в браузер за ≤ 500 мс при 50 тыс. строк в таблице, JavaScript начальной загрузки ≤ 300 КБ gzip. Пороги скорости и список страниц, которые меряются, — в одном файле: `tests/perf/pages.ts`. Проверки:

- **Замер скорости — `npm run perf`** (нужен `supabase start`; около трёх минут). В `npm run gate` не входит: в CI — только в контрольных точках (push в `main`, PR не в черновике, раз в неделю), локально — перед закрытием блока и когда меняется страница с данными. Playwright открывает страницы production-сборки в Chromium на компьютере и на телефоне по три раза, сравнивает медиану с порогом и печатает таблицу «страница × профиль × величина». Числа меряет сам браузер (Performance API):
  - сервер — заходом без троттлинга, потому что эмуляция сети прячет время сервера: TTFB (от запроса до первого байта) и «данные пришли» (от начала перехода до момента, когда строка из базы есть в документе; показ React может придержать ещё до 300 мс, чтобы экран не мигал, — эта пауза от сервера не зависит и в замер не входит);
  - отрисовка — под троттлингом Lighthouse через протокол DevTools: телефон — медленный 4G (562,5 мс на запрос, 1,47 Мбит/с) и процессор в 4 раза медленнее, компьютер — 150 мс на запрос и 9,2 Мбит/с. LCP и CLS — как их отдаёт браузер; TBT — сумма превышений 50 мс у долгих задач от первой отрисовки до окна тишины, как у TTI в Lighthouse: после загрузки 5 с без долгих задач и без завершённых запросов (задача, начатая и через секунды после загрузки, — ленивый график, таблица — в TBT попадает); оценка — формула Lighthouse по FCP, LCP, TBT и CLS (Speed Index браузер сам не меряет, в оценку он не входит).
  - Страницу за входом открывает пользователь замера со вторым фактором. Странице с данными замер одной командой SQL кладёт в таблицу 50 тыс. строк этого пользователя и после убирает их; следы вставки и удаления остаются в `audit.log` локальной базы (около 50 МБ за прогон) — их чистит `supabase db reset`.
  - Новая страница — запись в `MEASURED_PAGES`; страницу модуля дописывает `npm run new:module`. Страница `src/app` без записи и без причины в `NOT_MEASURED` (там же) — красный unit-тест `tests/unit/perf/measured-pages.test.ts`, он идёт в `npm run check` без браузера. Замер ловит грубое, от полусекунды: страницу, которая читает таблицу целиком, долгий запрос, тяжёлый скрипт. Снятый индекс на 50 тыс. строк стоит около 10 мс и по времени страницы не виден — индекс под запрос списка проверяется планом запроса (`explain`, скил `dev-kit:performance-budget`).
- **Объём JavaScript — `npm run budget`**: сумма gzip-скриптов из HTML каждой страницы, без префетча; сравнивает с базой `perf-baseline.json` — рост даже внутри лимита красный, пока базу не обновили осознанно: `npm run budget -- --update-baseline` в том же PR с объяснением; маршрут без записи в базе, запись без маршрута и страница без единого скрипта — тоже красные; когда все страницы рендерятся на запрос и HTML при сборке пуст (CSP с nonce, B00-T07), скрипты берутся из манифестов сборки — `--source manifest`, база и лимит те же. Разбор бандла — `npm run analyze`.
- **Лимит — граница, не цель.** Цель каждой задачи — не ухудшить метрики, а при возможности улучшить; улучшение тоже фиксируется в базе.
- **Рабочая версия:** время ответа страниц и медленные запросы к базе — Sentry на сервере; счётчиков в браузере нет (ТЗ 15.2, D-080, D-092).

Точка отсчёта шаблона (Next 16 + React 19): пустая страница ≈ 171 КБ gzip, главная с темой, уведомлениями и nuqs ≈ 211, страница с формой (zod, react-hook-form, Base UI) ≈ 258–264. В эти числа входит nomodule-полифилл (≈ 38 КБ): скрипт бюджета его считает, а современный браузер не скачивает — настоящая загрузка на столько же меньше. Лимит и база считаются вместе с полифиллом, так что лимит строже, чем выглядит. Текущие значения — в `perf-baseline.json`. Новый экран должен укладываться в бюджет: тяжёлые компоненты через `next/dynamic`, валидация на клиенте — только схемы из `domain`, серверные модули в клиент не импортировать.

Принципы: считать там, где данные (снимки и агрегаты в базе, индексы под фильтры, пагинация на сервере); кэш по умолчанию с точной инвалидацией по тегам; минимум JS в браузере (серверные компоненты, клиентские только листья, тяжёлое через `next/dynamic`, DTO вместо объектов целиком); мгновенный отклик (`useOptimistic`, `useTransition`, префетч, debounce); без водопадов (`Promise.all`, `React.cache` для дедупликации, `after()` для фоновой работы); один регион для приложения и базы (Vercel `fra1` в `vercel.json` и Supabase Frankfurt).

| Слой                    | Инструмент                                                        | Что проверяем                                                                                  |
| ----------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |

**Зависимости и lock-файл.** Node 24 и встроенный в него npm 11 (не ниже 11.19) — локально, в CI (`.nvmrc`) и на Vercel (`engines.node: 24.x`); версию npm требует сам репозиторий: `engines.npm: >=11.19.0` в `package.json` и `engine-strict=true` в `.npmrc` — более старый npm останавливает `npm install` и `npm ci` ошибкой `notsup`, а не молча выполняет install-скрипты зависимостей (он не понимает настройки ниже). Lock-файл пишет обычный `npm install`. На коммите lint-staged проверяет его сухим прогоном `npm@11.19.0 ci` (`scripts/check-lock.mjs`), чтобы CI не упал на рассинхронизации. Install-скрипты зависимостей не выполняются: решение по каждому пакету со скриптом записано в `allowScripts` в `package.json` (сейчас `fsevents` и `simple-git-hooks` — оба `false`, скрипт им не нужен; git-хуки ставит `prepare` самого проекта), а `strict-allow-scripts=true` в `.npmrc` останавливает установку пакета, по которому решения нет. Новый пакет со скриптом: `npm install <пакет> --ignore-scripts`, затем `npm install-scripts ls`, `npm install-scripts approve <пакет>` или `deny <пакет>` и строка D-NNN с причиной. Версия моложе трёх дней в lock-файл не попадает (`min-release-age=3`, как у Dependabot); срочное исправление уязвимости — `npm install <пакет>@<версия> --min-release-age=0`. TypeScript закреплён на `~6.0.3`: TypeScript 7 (компилятор на Go) пока без программного API, и typescript-eslint его не поддерживает — переход одной задачей, когда выйдут TypeScript 7.1 и поддержка в typescript-eslint; `@types/node` — по версии Node (24).
