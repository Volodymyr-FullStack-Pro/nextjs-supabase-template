# nextjs-supabase-template

Шаблон проекта с готовой архитектурой, правилами и проверками: Next.js 16 (App Router, Cache Components, React Compiler), Supabase (Auth, Postgres с RLS), Drizzle, строгий TypeScript (`@tsconfig/strictest`), shadcn/ui, next-safe-action + react-hook-form + Zod, nuqs, Intl-форматы денег и дат с часовым поясом проекта, ESLint 10 с проверкой архитектурных границ, Prettier, knip, jscpd, Vitest + Testing Library, Playwright, Lighthouse CI, pgTAP, lint-staged, GitHub Actions и настройки Claude Code с плагином `dev-kit`. С первого коммита весь пайплайн зелёный.

## Новый проект из шаблона

```bash
gh repo create <org>/<проект> --template Volodymyr-FullStack-Pro/nextjs-supabase-template --private --clone
cd <проект>
fnm use                      # Node 24 из .nvmrc (или nvm use)
npm ci                       # ставит зависимости и git-хуки
cp .env.example .env.local   # заполнить из Supabase → Project Settings → API
supabase start               # локальный Supabase (нужен Supabase CLI); supabase status → ключи в .env.local
npm run dev
```

Затем: заменить `<Проект>` в `CLAUDE.md` и `docs/knowledge/`, записать первое решение в `docs/knowledge/decisions.md`, первый модуль `npm run new:module <модуль> <запись>` — после разбиения ТЗ на блоки, при работе с ClickUp переименовать `.claude/rules/clickup.md.example` в `clickup.md`.

Безопасность: в Supabase выключить саморегистрацию (Authentication → «Allow new users to sign up» = off; пользователи заводятся приглашением), а если приложение закрыто Cloudflare Access — проверять его JWT в `proxy.ts` или закрыть `*.vercel.app`, иначе периметр обходится (`.claude/rules/security.md`). В репозитории включить оповещения Dependabot и автоматические security-PR (`gh api -X PUT repos/<org>/<проект>/vulnerability-alerts` и `.../automated-security-fixes`), защитить `main` (PR и зелёный CI обязательны). Версия Supabase CLI в `.github/workflows/db.yml` закреплена и должна совпадать с `supabase --version` на машинах разработчиков: обновлять обе вместе.

Второй фактор и журнал изменений уже в шаблоне. Вход по паролю дополняется кодом из приложения-аутентификатора (TOTP): экраны `/mfa/setup` и `/mfa/verify` в модуле `auth`; у кого фактор подключён, тот после пароля попадает на `/mfa/verify`, а с `AUTH_REQUIRE_MFA=true` (финансовые проекты) без фактора — на `/mfa/setup`. Проверяют три места: `src/proxy.ts` (редирект), `authActionClient` (Server Action отказывает) и база — ограничивающая политика `private.mfa_ok()` на каждой таблице: с подтверждённым фактором строки видны только в сессии `aal2`. Журнал `audit.log` (схема `audit`, закрыта для API) пишет триггер `audit.record()`: кто, когда, операция, старая и новая строка. Новая таблица получает ту же политику и тот же триггер (образец — миграции `*_second_factor_policies.sql` и `*_audit_log.sql`). Цена: в сессии `aal1` проверка фактора — запрос к Supabase Auth (`listFactors`) в `proxy.ts` и в `verifySession`; в `aal2` запросов нет.

Для `/notes`, `npm run db:types`, pgTAP и e2e за входом (`npm run test:e2e:db`) нужны Docker и Supabase CLI (`brew install supabase/tap/supabase`). Первого пользователя заведите в Studio (`http://127.0.0.1:54323` → Authentication → Add user) или через `supabase/seed.sql`.

Хостинг и выпуск — [docs/release.md](docs/release.md): Vercel в регионе Франкфурт (`fra1` в `vercel.json`), Supabase в регионе Frankfurt, миграции и настройки Auth на staging и production выкладывает `deploy-db.yml`, ошибки сервера — Sentry (`src/instrumentation.ts`, организация в регионе EU).

## Архитектура: модули и четыре слоя

Код разложен по доменам (модулям), внутри модуля — по слоям. Правило одно: зависимости направлены внутрь, к чистому ядру; фреймворки и база — снаружи и заменяемы. Нарушение правила — ошибка `npm run lint`, а не замечание на ревью.

### Что это за архитектура

Это **модульный монолит**: одно приложение, одна база и один деплой, а внутри — независимые модули с проверяемыми границами. Каждый модуль устроен по **чистой архитектуре** (порты и адаптеры): в центре правила, снаружи база и фреймворк. Подход собран из проверенных практик, а не придуман заново:

| Откуда                              | Что взяли                                                                                                                                         |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Domain-Driven Design                | модуль — предметная область целиком (ограниченный контекст): бизнесы, инвестиции, обязательства; у каждой свои данные, правила, сценарии и экраны |
| Чистая и гексагональная архитектура | слои `domain` → `application` → `infrastructure` и `ui`, зависимости только внутрь; база подключается через порт (интерфейс), а не напрямую       |
| Вертикальные срезы                  | всё по одной области лежит в одной папке, а не разбросано по общим папкам «контроллеры», «сервисы», «модели»                                      |
| Модульный монолит                   | модули живут в одном приложении и не лезут друг другу во внутренности; когда понадобится, модуль выносится в отдельный сервис                     |

Чем это не является: не Feature-Sliced Design (там слои общие на всё приложение, а фича — одно действие пользователя; модуль здесь ближе к модулю Angular или NestJS), не MVC с папками по типу файлов и не микросервисы с первого дня (они дороги в разработке и эксплуатации, пока нагрузка и команда этого не требуют).

### Папки

```
src/app/                         тонкие page/layout: только композиция и Suspense, никакой логики
src/modules/<домен>/
  domain/                        модели (Zod), чистые правила, ошибки домена. Без React, Next, Supabase, Drizzle
  application/                   use cases и интерфейсы репозиториев (порты)
  infrastructure/                реализации портов: Supabase/Drizzle, внешние API; *.fake.ts — для тестов
  ui/                            actions (next-safe-action → use case), формы, компоненты, search-params
  server.ts                      точка сборки: use cases с реальными репозиториями (единственный «DI»)
src/shared/
  domain/                        деньги (decimal.js), Result, ошибки домена, текст, даты и часовой пояс
  infrastructure/                клиенты Supabase, схема Drizzle и прямое подключение, env
  lib/                           safe-action (actionClient, mfaActionClient, authActionClient, fail), session, runtime
  ui/                            shadcn/ui, form/TextField, SubmitButton, sonner
src/proxy.ts                     обновление сессии и редиректы (не единственная защита)
```

Простыми словами, на примере модуля `businesses`:

| Папка                       | Что это                                                                                        | Пример                                                                                                           |
| --------------------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `src/app`                   | адреса страниц: какой экран открывается по какому URL; сами ничего не считают и не читают базу | `src/app/businesses/page.tsx` показывает список бизнесов                                                         |
| `domain`                    | что такое запись и какие у неё правила; чистый TypeScript без базы, React и Next               | схема бизнеса: доля от 0 до 100 %, оценка не меньше нуля; ошибка «доля больше 100 %»                             |
| `application`               | что с записью можно делать (сценарии) и что для этого нужно от хранилища (порт)                | `create-business.ts`, `list-businesses.ts`; `businesses-repository.ts` — «сохранить, найти, список» без Supabase |
| `infrastructure`            | как это хранится и откуда приходит                                                             | `businesses-repository.supabase.ts` — запросы к базе; `businesses-repository.fake.ts` — хранилище для тестов     |
| `ui`                        | как это выглядит и как отправляется                                                            | форма, список, action сохранения, параметры поиска в URL                                                         |
| `server.ts`                 | сборка модуля: сценарии с настоящей базой; через него модуль видят страницы и другие модули    | `businesses.list(...)`, `businesses.create(...)`                                                                 |
| `src/shared/domain`         | общие правила для всех модулей                                                                 | деньги, `Result`, ошибки, нормализация текста, даты                                                              |
| `src/shared/infrastructure` | общие подключения                                                                              | клиенты Supabase, Drizzle, переменные окружения                                                                  |
| `src/shared/lib`            | общая техника Next.js                                                                          | безопасные actions, сессия                                                                                       |
| `src/shared/ui`             | общие элементы интерфейса                                                                      | кнопки, поля, карточки shadcn                                                                                    |
| `src/proxy.ts`              | входная дверь: выполняется до любой страницы                                                   | обновляет сессию и отправляет незалогиненных на вход                                                             |

Кто куда может обращаться:

| Слой             | Что в нём                 | Может импортировать                                                                                                           |
| ---------------- | ------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `domain`         | модели, правила, ошибки   | свой `domain`, `shared/domain`, пакеты без I/O (zod, decimal.js)                                                              |
| `application`    | use cases, порты          | свой `domain` и `application`, `shared/domain`                                                                                |
| `infrastructure` | репозитории, шлюзы, фейки | свой `application` и `domain`, `shared/domain`, `shared/infrastructure`                                                       |
| `server.ts`      | сборка                    | свой `application`, `infrastructure`, `domain`, `shared/*` кроме `ui`                                                         |
| `ui`             | actions, компоненты       | свой `server.ts`, `domain`, `ui`; `shared/ui`, `shared/lib`, `shared/domain`; чужие модули — только их `server.ts` и `domain` |
| `app`            | маршруты                  | `modules/*/ui`, `modules/*/server.ts`, `modules/*/domain`, `shared/ui`, `shared/lib`, `shared/domain`                         |

`domain` и `application` из пакетов npm могут импортировать только `zod` и `decimal.js` (и `date-fns`, если проект его добавит) — всё остальное запрещено `eslint-plugin-boundaries` (конфигурация в `eslint.config.mjs`). Тесты живут в `tests/unit`, зеркалом `src`: рядом с кодом они нарушили бы границы. Barrel-файлы (`index.ts` с реэкспортом) не используются: импорт по точному пути, это быстрее собирается и лучше анализируется.

### Преимущества

- **У каждой вещи одно место.** Любой модуль устроен одинаково: новый человек разбирается за минуты, ревью короче, Claude Code не выбирает, «куда положить».
- **Правила проверяются за миллисекунды.** Расчёты денег и бизнес-правила — чистые функции в `domain`: тесты идут без базы и браузера, покрытие `domain` — 100 %.
- **Архитектура не расползается.** Границы проверяет линтер на каждом коммите и в CI, а не память людей: через год код устроен так же, как в первый день.
- **Модули не мешают друг другу.** Правка в одном модуле не ломает другой; несколько человек работают параллельно почти без конфликтов в git.
- **Замена без переписывания.** Другая база, внешний сервис или библиотека интерфейса меняют один слой; правила и экраны остаются.
- **Безопасность по умолчанию.** Данные читаются только через сценарий с `userId` и клиент с RLS: чужие строки база не отдаст, даже если в коде ошибка.
- **Скорость не страдает.** Слои — это папки и импорты, а не обёртки во время работы: нет DI-контейнера, рефлексии и лишнего JavaScript в браузере; страницы остаются серверными компонентами с кэшем Next.js.
- **Просто и дёшево в эксплуатации.** Одно приложение и одна база: один деплой, одни логи, обычные транзакции без распределённых протоколов.
- **Рост без переезда.** Нагруженный модуль выносится в отдельный сервис, не задевая остальные (см. «От лендинга до высоконагруженной системы»).

**Цена.** На старте файлов больше, чем в «одной папке с компонентами»: на одну запись — модель, сценарий, порт, репозиторий, фейк и тесты. Каркас создаёт генератор, поэтому это минуты, а не часы. Страницам без данных (лендинг) слои не нужны вовсе: там работают только `src/app` и `shared/ui`.

### Как проходит запрос

1. **Чтение.** `page.tsx` рендерит статическую оболочку и оборачивает динамику в `<Suspense>`. Серверный компонент из `ui/` берёт сессию (`verifySession`) и вызывает use case из `server.ts`; use case ходит в порт, порт реализован на user-scoped клиенте Supabase (RLS применяется). Наружу уходит модель домена, не строка таблицы.
2. **Запись.** Форма (`useHookFormAction` + Zod-схема из `domain`) вызывает action из `ui/actions.ts`. `authActionClient` проверяет сессию в middleware и валидирует вход той же схемой; action вызывает use case, получает `Result`, при ошибке домена делает `fail(error)` (клиенту уходит код ошибки и правило, не текст), затем обновляет данные: `updateTag(tag)` для кэшированных, `refresh()` для динамических на текущей странице.
3. **Ошибки.** Ожидаемые (`NotFoundError`, `ForbiddenError`, `ConflictError`, `RuleViolationError`) возвращаются из use case как `Result` с кодом (`code`, у правила ещё `rule`); `domain` и `application` текстов для пользователя не содержат, сообщения Zod — тоже ключи. Тексты — в словаре модуля `ui/messages.ts` (`satisfies Record<ключ | код, string>`, неполный словарь — ошибка типов), общие — в `src/shared/ui/form/messages.ts`; форма показывает их через `failureMessage` и `TextField messages={…}`. Язык один — `DEFAULT_LOCALE` (`src/shared/domain/locale.ts`: `lang`, деньги, даты); второй язык — next-intl по тем же ключам. Неожиданные (сеть, база) бросаются и превращаются в общую фразу в `handleServerError`; причина уходит строкой JSON в лог и в Sentry (`src/shared/infrastructure/monitoring.ts`; Sentry включается переменной `SENTRY_DSN`, `docs/release.md`).
4. **Кэш.** Данные пользователя читаются динамически под Suspense. Справочники и редко меняющиеся данные — компоненты и функции с `'use cache'`, `cacheLife`, `cacheTag`; инвалидация — `updateTag(tag)` (или `revalidateTag(tag, 'max')`, в Next 16 второй аргумент обязателен) в action, который их меняет. Внутри `'use cache'` нельзя читать cookies и сессию.

### Новый модуль

```bash
npm run new:module businesses business
```

Как `ng generate` в Angular: одинаковый каркас с тестами. Создаёт `src/modules/businesses/{domain,application,infrastructure,ui}`, `server.ts`, фейк репозитория, тесты домена и use case и страницу `src/app/businesses/page.tsx`. Всё проходит `npm run check` сразу; дальше описываете модель в `domain`, use cases в `application`, запросы в `infrastructure`. Action и форму генератор не создаёт: образец — `src/modules/notes/ui/actions.ts` и `notes-form.tsx`.

**Модули и чужие данные.** Из `ui` и `app` чужой модуль доступен через его `server.ts` (use cases) и `domain` (типы). Внутри `application` и `infrastructure` чужие use cases не вызываются: агрегирующий модуль (например, портфель, которому нужны бизнесы и инвестиции) описывает свой порт и реализует его своим репозиторием поверх таблиц или представления в базе. Так модули остаются независимыми, а агрегаты считаются там, где данные.

### От лендинга до высоконагруженной системы

Правило зависимостей, слои и тесты одинаковы на любом масштабе; меняется только то, что добавляется вокруг них.

| Масштаб                                | Как устроено                                                                                                                         | Что добавляется                                                                                                                                                                                                                              |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Лендинг, сайт-визитка                  | страницы в `src/app/(marketing)` и компоненты `shared/ui`; модуль — только там, где есть данные (например, `leads` для формы заявки) | статическая отдача и CDN Vercel, `'use cache'`                                                                                                                                                                                               |
| Кабинет, внутренняя система, учёт, CRM | модуль на каждую предметную область; правила — в `domain`, права — RLS и use cases                                                   | плановые задачи `src/app/api/cron/*`, реестр требований, блоки поставки                                                                                                                                                                      |
| SaaS для многих компаний               | плюс модуль `organizations`, колонка `organization_id` и RLS по членству; организация — в контексте use case рядом с `userId`        | роли, тарифы, письма                                                                                                                                                                                                                         |
| Растущая нагрузка                      | те же модули, без перестройки                                                                                                        | кэш с тегами, агрегаты и индексы в базе, пагинация на сервере, пул соединений (Supavisor), реплики чтения Supabase, очередь для долгих задач (Supabase Queues или Trigger.dev)                                                               |
| Высокая нагрузка, несколько команд     | модули становятся пакетами монорепозитория, у каждого — своя команда                                                                 | нагруженный модуль выносится в сервис: его `domain` и `application` переезжают без изменений, в приложении остаётся адаптер в `infrastructure`, который ходит в сервис по HTTP или через очередь; страницы и другие модули этого не замечают |

Отдельная служба рядом с приложением нужна для постоянных соединений в реальном времени (Supabase Realtime), тяжёлых вычислений и долгих сценариев с повторами. Основное приложение при этом остаётся модульным монолитом.

### Типовые расширения

| Нужно                                   | Что делать                                                                                                                                                                              |
| --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Второй язык интерфейса                  | `next-intl` без языка в адресе: язык из профиля или cookie; словари `ui/messages.ts` уже по ключам и кодам и переносятся как есть, модули не меняются                                   |
| API для мобильного приложения           | Route Handlers в `src/app/api/...` вызывают те же use cases; вход по токену `Authorization: Bearer` — отдельный клиент Supabase и проверка в `proxy.ts` (сейчас сессия только в cookie) |
| Другая база или внешний сервис          | новая реализация порта в `infrastructure` модуля; `domain`, `application` и `ui` не меняются                                                                                            |
| Другой способ входа                     | `src/shared/lib/session.ts` и `src/proxy.ts`; use cases получают `userId` как раньше                                                                                                    |
| Фоновые задачи, расписание, уведомления | `src/app/api/cron/*` и `after()`; долгие — очередь, когда понадобится                                                                                                                   |

## Чистый код

Линтер держит код простым и читаемым, а правила и ревью — осмысленным: без комментариев (смысл в именах, структуре и тестах, причины решений — в журнале `docs/knowledge/decisions.md`; разрешены только директивы инструментов), файл ≤ 300 строк (потолок; единую ответственность держат лимиты на функцию), функция ≤ 80 строк (компонент `.tsx` ≤ 120) и ≤ 3 параметров, сложность ≤ 10, без магических чисел, имена без сокращений и одиночных букв, kebab-case файлов, `eslint-disable` только с именем правила (проверяет линтер) и причиной в той же строке (проверяет ревью). Принципы DRY (на третьем повторе), KISS, YAGNI, честный TypeScript и неизменяемость — в скиле `dev-kit:code-style`, особенности шаблона — в `.claude/rules/code-style.md`. Компоненты shadcn в `src/shared/ui` — сторонний код: к ним применяются только границы импортов. Корневые конфиги (`eslint.config.mjs`, `vitest.config.mts` и т. п.) и SQL могут содержать комментарии — правило «без комментариев» действует на `src`, `scripts` и `tests`.

**Типы, ввод, повторы.** `any` запрещён; `unknown` и `as` линтер допускает только там, где данные приходят извне (`infrastructure`, `shared/lib`, `app/api`, `proxy.ts`) и тут же проходят Zod. Текст пользователя нормализуется один раз в Zod-схеме `domain` (`normalizeText` из `src/shared/domain/text.ts`: NFC, без невидимых символов, схлопнутые пробелы), поиск — `normalizeSearch` в use case. Импорты сортирует и группирует линтер (`simple-import-sort`, `import/no-duplicates`, `consistent-type-imports`); barrel-файлов нет — короткие импорты даёт `server.ts` модуля. Формы отправляются через `SubmitButton` (блокировка, `aria-busy` и спиннер на время action); операции, которые пользователь может повторить, идемпотентны (`client_request_id`), индексы строятся под запросы списков — скил `dev-kit:supabase-rls-drizzle`. Базовые заголовки безопасности — в `next.config.ts`.

**Дизайн и качество интерфейса.** Выбор заказчика записывается в `docs/design/design-system.md`, значения — токенами в `src/app/globals.css`; цвет значением в коде ловит линтер. E2E идёт на компьютере (Chrome 1440×900) и на iPhone (Safari); `tests/e2e/ui-quality.spec.ts` проверяет доступность WCAG 2.2 AA (axe) в светлой и тёмной теме и отсутствие горизонтальной прокрутки. Порядок «варианты дизайна заказчику → выбор → код» — скил `dev-kit:design-system`.

## Производительность

Бюджет на маршрут: TTFB ≤ 200 мс с кэшем, LCP ≤ 1,5 с, TBT ≤ 200 мс, CLS ≤ 0,1, Lighthouse Performance ≥ 90, JavaScript начальной загрузки ≤ 300 КБ gzip. Проверки:

- **Лаборатория, на каждом PR:** Lighthouse на компьютере и на телефоне (`lighthouserc.cjs`, `lighthouserc.mobile.cjs` с эмуляцией телефона, порогами LCP 2,5 с и TBT 400 мс (на раннере CI телефон даёт 200–235 мс); `npm run perf`), `npm run budget` (сумма gzip-скриптов из HTML каждой страницы, без префетча; сравнивает с базой `perf-baseline.json` — рост даже внутри лимита красный, пока базу не обновили осознанно: `npm run budget -- --update-baseline` в том же PR с объяснением), e2e-замер TTFB главной, `npm run analyze` для разбора бандла.
- **Лимит — граница, не цель.** Цель каждой задачи — не ухудшить метрики, а при возможности улучшить; улучшение тоже фиксируется в базе.
- **Поле, в проде:** Web Vitals реальных пользователей (`src/app/web-vitals.tsx` → `/api/vitals`): LCP, INP, CLS, FCP, TTFB с оценкой good / needs-improvement / poor. Сейчас пишутся в лог структурированной строкой; в проекте подключить Sentry или аналитику в `src/app/api/vitals/route.ts`.

Точка отсчёта шаблона (Next 16 + React 19, без nomodule-полифилла): пустая страница ≈ 172 КБ gzip, главная с темой, уведомлениями, nuqs и Web Vitals ≈ 210, страница с формой (zod, react-hook-form, Base UI) ≈ 260. Текущие значения — в `perf-baseline.json`. Новый экран должен укладываться в бюджет: тяжёлые компоненты через `next/dynamic`, валидация на клиенте — только схемы из `domain`, серверные модули в клиент не импортировать.

Принципы: считать там, где данные (снимки и агрегаты в базе, индексы под фильтры, пагинация на сервере); кэш по умолчанию с точной инвалидацией по тегам; минимум JS в браузере (серверные компоненты, клиентские только листья, тяжёлое через `next/dynamic`, DTO вместо объектов целиком); мгновенный отклик (`useOptimistic`, `useTransition`, префетч, debounce); без водопадов (`Promise.all`, `React.cache` для дедупликации, `after()` для фоновой работы); один регион для приложения и базы (Vercel `fra1` в `vercel.json` и Supabase Frankfurt), прямое подключение — через пул Supavisor.

## Тесты

| Слой                    | Инструмент                                                        | Что проверяем                                                                                  |
| ----------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `domain`, `application` | Vitest на фейках из `infrastructure/*.fake.ts`                    | правила и use cases без базы; покрытие `domain` 100 %, `application` 100 % строк и 95 % ветвей |
| клиентские компоненты   | Vitest + Testing Library в jsdom (`// @vitest-environment jsdom`) | поведение, доступность; URL — `withNuqsTestingAdapter`                                         |
| страницы и сценарии     | Playwright против production-сборки и локального Supabase         | серверные компоненты, формы, вход, RLS глазами пользователя, TTFB                              |
| политики RLS            | pgTAP (`supabase test db`)                                        | свои строки видны, чужие нет                                                                   |
| внешние HTTP            | MSW (добавляется с первым внешним API)                            | ответы записаны, сеть не мокается на уровне функций                                            |

Имена тестов: начинаются с глагола в третьем лице и описывают намерение, не реализацию: `it('rejects an empty title')`, `it('lists only the notes of the current user')`. Без `should`, `tests`, `must`; контекст — в названии файла; один тест — одно поведение; в тестах правил домена номер требования из реестра — в имени теста (`(B03-AC-02)`).

## Что где лежит

- `src/app` — только маршруты, layout, `error.tsx`, `global-error.tsx`, `not-found.tsx`.

- `supabase/migrations` — источник правды для базы; `supabase/tests` — pgTAP; `supabase/config.toml` — локальный стек.
- `tests/unit` (зеркалит `src`), `tests/e2e`.
- `scripts/` — `new-module.mjs` (каркас модуля), `requirements-check.mjs` (реестр требований), `bundle-budget.mjs` (бюджет JS; страница без HTML — ошибка), `check-lock.mjs` (lock-файл для npm 11, как в CI и на Vercel), `with-local-supabase.mjs` (команда с адресом и ключами локального Supabase).
- `.claude/` — `settings.json` (маркетплейс `claude-kit`, плагин `dev-kit`, разрешения: команды проверок и удаление на GitHub веток, уже слитых в `main`; запреты: чтение `.env*` с ключами, удаление в ClickUp), `rules/` (архитектура, безопасность, база, интерфейс, тесты, документация).
