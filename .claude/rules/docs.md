# Документация и процесс

## Архитектура — `docs/architecture.md`

- Единственное место действующих решений: архитектура, правила кода, бизнес-правила заказчика, ставшие правилами системы. Только то, что верно сейчас; история — журнал. Запись — внутри раздела, четыре пункта: «Решение / Почему / Для кода / Основание».
- Архитектурное решение — хотя бы один признак: касается больше одного модуля или задачи; дорого отменить (форма данных, деньги, доступ, размещение, внешний контракт); задаёт правило всему коду; компромисс по стоимости, безопасности или скорости; бизнес-правило заказчика стало правилом системы. Процесс (ClickUp, ревью, ритм CI) и разовые решения одной задачи — не архитектура.
- Развилка с такими признаками посреди задачи — стоп и вопрос человеку с рекомендацией; Claude сам не решает.
- После «да» — тем же коммитом, что и работа: строка D-NNN с пометкой `→ architecture.md` в статусе, у крупного — ещё `decisions/D-NNN.md`, запись в `architecture.md`, в коде — `// D-NNN: …`. Урок задачи в «Коротко для проверки» отмечает «архитектура: добавлено / изменено …».
- Решение заменено — запись в `architecture.md` переписывается под новое, строка старого в журнале получает статус «заменено D-MMM» без пометки.
- Старт блока — Claude называет разделы `architecture.md`, которые блок затрагивает, человек их перечитывает; закрытие блока — пункт «`architecture.md` соответствует коду».

## Роли и пределы файлов знаний

`npm run docs:check` (`scripts/docs-check.mjs`, входит в `check` и CI) проверяет пределы в числах и что ссылки `architecture.md` на решения сходятся с пометками журнала в обе стороны: превышено или разошлось — красный. Не проверяет: блоки и спринты roadmap (держит ревью), урок задачи (его нет в git, состав держит `/dev-kit:explain`), память Claude (вне репозитория). Числа — `LIMITS` в `scripts/docs-limits.mjs`; тест `docs-limits.test.ts` сверяет их с этой таблицей, менять — вместе.

## Жизнь документов

- Рабочий документ (план, заметка, временная копия) удаляется в той задаче, где перестал быть нужен: историю держит git. Архив — только у документов заказчика в `docs/client/`.
- Статус проекта — только «Сейчас» в `docs/roadmap.md`: он переписывается, а не дописывается. Таблицы «Статус» в других документах не ведутся.
- Задача вне блока с планом `docs/plans/<тема>.md` закрывается на «задача проверена» так же, как задача блока: план удалён, «Сейчас» переписано, итог — комментарием «Сделано / Результат» в карточку ClickUp.
- `npm run docs:check` (`scripts/docs-structure.mjs`) ловит: план в `docs/plans/`, не названный в «Сейчас»; файл в `docs/`, на который или на папку которого не ссылается ни один другой файл (кроме `docs/client/` и `docs/knowledge/decisions/`); markdown-ссылку на путь, которого нет в git. Ссылка на папку покрывает только файлы прямо в ней; путь в обратных кавычках считается ссылкой, только если начинается с `docs/`; упоминания в истории (журнал, `decisions/`, `docs/client/`, handoff) ссылкой не считаются. Не видит: старый путь в обратных кавычках, устаревший текст в живом файле и файл, на который ссылается только такой же забытый файл, — это держат ревью и уборка раз в спринт.

## Остальное

- Решение — строка D-NNN в конец журнала; решение, меняющее архитектуру, стек, процесс, безопасность или деньги, — плюс `decisions/D-NNN.md` по шаблону `decisions/_template.md`.
- Факт о коде проекта (имя файла, команда, правило линтера, образец) живёт в одном месте — в правиле `.claude/rules/` рядом с линтером, который его проверяет. Скил плагина формулирует принцип и ссылается на правило; `CLAUDE.md`, README и задачи блоков указывают на него, а не пересказывают. Нашёл вторую копию — оставить одну и поставить ссылку.
- Новая сущность (таблица, модуль, экран) — три задачи в `tasks.md`: база и pgTAP; ядро и unit-тесты; экран и e2e. Срез целиком создаёт `npm run new:module` в первой задаче отдельным коммитом `wip: BNN-TNN generator slice` — он уже проходит `npm run gate`, это доказывает `npm run generator:check`. Дальше каждая задача доводит свой слой под сущность, а её урок показывает отличия от созданного, а не созданные файлы: (1) миграция, pgTAP, типы; (2) модель, правила, use cases, репозиторий, фейк, unit; (3) форма, список, тексты, e2e. Правка соседнего слоя, без которой `gate` не зелёный (переименована колонка — строка колонок в репозитории), делается в той же задаче.
- Результат задачи пишется один раз — «Итог» под задачей в `tasks.md`; в описание PR — его английская версия, в подзадачу ClickUp — короткий пересказ для менеджера без технических деталей.
- Настройка, сделанная вне репозитория (GitHub, Supabase, Vercel), сохраняется файлом с командами или выгрузкой, как `docs/ops/github/branch-protection.json`: её можно проверить и повторить, урок задачи ссылается на файл.

Подробно: путь задачи, блоки, ветки и PR — скил `dev-kit:delivery`; ответы заказчика — `dev-kit:requirements-register`; карточки ClickUp — `dev-kit:clickup-card`.
