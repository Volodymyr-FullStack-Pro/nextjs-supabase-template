# База данных: таблицы, журнал, соглашения

- Ссылка на `auth.users` — `on delete restrict`, не `cascade`: удаление пользователя не стирает финансовые строки и автора в журнале. На аудируемой таблице — `before truncate … execute function audit.forbid_truncate()`: `truncate` обходит построчный журнал (образец — `*_notes_sample_hardening.sql`, pgTAP `004`).
- Журнал `audit.log` защищён триггером от правки, удаления и очистки через SQL-редактор и прямое подключение к базе; от владельца, который снимет триггер (`disable trigger`, `session_replication_role`), он не защищён — это уровень доступа к панели Supabase, а не кода.
- Историю записи журнал находит по `(table_name, row_id)`: `audit.record()` берёт `row_id` из строки до изменения и отклоняет `update`, который меняет `id`, — для любой роли, включая владельца базы (`42501`; `*_audit_record_identity.sql`, pgTAP `007`). Поэтому у аудируемой таблицы ключ — одна колонка `id`, и клиент её не задаёт и не меняет.
- Образец таблицы — `notes`: политики и индекс — `supabase/migrations/20260101000000_notes.sql`, колоночные права — `*_notes_column_grants.sql`, валюта и ключ повтора — `*_notes_currency_and_request_id.sql` (новая таблица пишет всё это одной миграцией); pgTAP таблицы — `supabase/tests/001`, `004`, `005` (журнал и второй фактор проверяют `003` и `002` на своих таблицах — они остаются после удаления примера), репозиторий — `src/modules/notes/infrastructure/notes-repository.supabase.ts`; та же таблица одной миграцией, её pgTAP и репозиторий — шаблоны генератора `scripts/module-template/` (`supabase/migrations/__module_name__.sql`, `supabase/tests/__module-name__.sql`, `…/infrastructure/__module-name__-repository.supabase.ts`): `npm run new:module` создаёт из них таблицу модуля, а `npm run generator:check` доказывает, что она проходит `900` без исключений, — они остаются образцом после удаления примера (B00-T03). Другие формы доступа и функции — `examples.md` скила `dev-kit:supabase-rls`; первая таблица продукта называется в этой строке.
- Каждая таблица с данными пользователя, кроме политик владельца: ограничивающая политика второго фактора `as restrictive for all to authenticated using ((select private.mfa_ok())) with check ((select private.mfa_ok()))` и триггер журнала `after insert or update or delete … for each row execute function audit.record()` (образцы — `*_second_factor_policies.sql`, `*_audit_log.sql`). Схемы `private` и `audit` в Data API не открываются.
- Соглашения базы у каждой таблицы `public` проверяет по каталогу `supabase/tests/900-table-conventions.sql`: RLS; разрешающая политика, и не `using (true)`; политика второго фактора; триггеры журнала и запрета `truncate`; колонка `id`; ничего у `anon`; у `authenticated` `insert` и `update` только по колонкам, без `truncate`, `references`, `trigger`; служебные колонки вне этих прав (`id`, `created_at`, `updated_at` — ни в `insert`, ни в `update`; `owner_id` и `client_request_id` — не в `update`); внешние ключи без `cascade` и `set null` и с индексом; нет `money`, `real`, `double precision`; `check` на `NaN` у каждой `numeric`; валюта рядом с суммой — типы сверяются по базовому типу, так что домен над `numeric` или `double precision` проверки не обходит (проверка `NaN` может стоять на колонке или на домене); функции `public` без `numeric` в аргументах и результате; `security definer` функции для `authenticated` — с проверкой сессии и второго фактора в теле. `supabase db advisors --fail-on warn` ничего из этого не ловит (внешний ключ без индекса и RLS без политик у него — уровень INFO). Упавшая проверка называет таблицу или колонку и текст для миграции. Осознанное исключение (справочник, который читают все вошедшие; таблица без журнала) — строка в `convention_exceptions` в начале теста: таблица (для соглашений одной колонки — служебные колонки, `float`, `NaN`, валюта — можно `таблица.колонка`, чтобы исключение не прятало соседние колонки) или функция, ключ соглашения, причина с номером D-NNN; у включённого RLS исключений нет. Поведение политик — свой видит, чужой нет — этот тест не проверяет: оно остаётся в pgTAP самой таблицы.
- pgTAP: `tests.authenticate_as('alice', 'aal2')` — сессия со вторым фактором, `tests.add_verified_totp('alice')` — подтверждённый TOTP. Хелперы остаются в базе после `supabase test db`, поэтому команда — только локально (не `--remote`): `.claude/settings.json` запрещает Claude `supabase test db`, `migration up`, `db lint` и `db advisors` с `--remote`, `--linked` и `--db-url`.
- Типы колонок: `uuid default gen_random_uuid()`; момент — `timestamptz` (UTC), не `timestamp`; учётный период и дата без времени (месяц отчёта, дата закрытия) — `date`; `text` + `check (char_length(…) <= N)` вместо `varchar(N)`; `boolean not null default …`; перечисление — `text` + `check`, `enum` — только для устоявшихся наборов.

API, миграции и функции для `rpc` — `db.md`; деньги и повтор записи — `db-money.md`.

Подробно: скил `dev-kit:supabase-rls`; перед любым изменением базы — `postgres-best-practices:supabase-postgres-best-practices`.
