# Архитектура: модули и четыре слоя

- Опорные файлы: `src/shared/domain/result.ts` (`ok`, `err`), `src/shared/domain/errors.ts`, `src/shared/lib/safe-action.ts` (`authActionClient`, `mfaActionClient` для экранов `/mfa/*`, `setupActionClient` — подключение TOTP, `actionClient`, `fail`); образец модуля целиком — `src/modules/notes`.
- Новый модуль — `npm run new:module <модуль> <запись>` (`scripts/new-module.mjs`), руками срез не собирать. Генератор разворачивает шаблоны `scripts/module-template/` в полный срез с рабочими полями `title`, `amount`, `currency`: четыре слоя и `server.ts`, форма, список, словарь, action, страница с `<Suspense>`, одна миграция таблицы, её pgTAP, unit и e2e; страницу и таблицу сам дописывает в списки e2e (`SIGNED_IN_PAGES`, `OWNED_TABLES`). `npm run gate` проходит после `supabase migration up && npm run db:types` и `npm run budget -- --update-baseline` — их генератор печатает в конце. Шаблоны — исполняемый образец: это те же файлы, что в примере `notes`, с метками вместо имён (`notes-form.tsx` ↔ `ui/__module-name__-form.tsx`), и после удаления примера правила ссылаются на них. Метка пишется в том регистре, в каком нужно имя: `__module-name__` → `bank-accounts`, `__module_name__` → `bank_accounts`, `__moduleName__`, `__ModuleName__`, `__MODULE_NAME__`; для одной записи — те же пять с `entity`.
- Шаблоны стоят вне линтера, `tsc` и покрытия, поэтому их проверяет `npm run generator:check`: создаёт модуль `generator-probes`, применяет миграцию и прогоняет на нём всё, что входит в `gate` (линтер и его самопроверку, типы, unit с порогами, knip, jscpd, prettier, advisors, db lint, pgTAP, Squawk, e2e модуля на двух устройствах, бюджет JS) и замер скорости его страницы на 50 тыс. строк (`npm run perf`), затем удаляет модуль и таблицу — файлы и база остаются такими, какими были до запуска, в том числе незакоммиченные правки. Пока она идёт, исходные версии изменяемых файлов и список созданных лежат в снимке `node_modules/.cache/generator-check/snapshot.json`: прерванную без уборки проверку (закрытый терминал, `kill -9`, падение) следующий запуск сначала возвращает по нему. Остатки модуля без снимка, расхождение файлов миграций с базой и неотвечающую базу она называет и останавливается, ничего не удаляя; удаляет только то, что создала сама. Нужны `supabase start` и свободные порты e2e. Запускать после правки шаблонов, общего кода, на который они опираются (`src/shared`; файлы `tests/e2e/support`, которые e2e шаблонов импортируют прямо или через другой файл), правил линтера и pgTAP `900`; в CI — только в контрольных точках (push в `main`, PR не в черновике), в `npm run gate` не входит.
- Границы слоёв и пакеты, разрешённые `domain` и `application` (`zod`, `decimal.js`), задаёт `boundaries` в `eslint.config.mjs`. Ошибка границ значит, что код не на своём месте: переложить, не `eslint-disable`.
- Защиты `local/*` там же (сообщение правила говорит, как исправить; пробы — `tests/lint-rules/fixtures`): use case не бросает исключений — ожидаемый отказ `return err(…)`, нарушенный инвариант — из функции `domain` (`local/no-throw-in-use-case`); `Result` проверяется — `if (!result.ok) fail(result.error)` (`local/no-ignored-result`); каждый экспорт файла `'use server'` — цепочка `authActionClient`, владелец — из `ctx.session`, не из входа (`local/server-action`); клиент actions собирает только `src/shared/lib/safe-action.ts` — пакет `next-safe-action` больше никто не импортирует, кроме хуков и типов (`local/action-client`); `verifySession`, `actionClient`, `mfaActionClient`, `setupActionClient` — только модуль `auth` (`local/behind-sign-in`); клиент Supabase, секретный ключ, драйвер Postgres и `admin` — обход RLS, где что разрешено — `security.md` (`local/raw-client`, `local/direct-database`, `local/dynamic-import`); репозиторий проверяет `error`, выбирает колонки списком и не зовёт `getSession()` (`local/data-access`), а ошибку базы и Auth бросает как операцию и код — `throw databaseError('модуль.действие', error)`, не `error.message` и не `cause` (`local/error-by-code`); ответ PostgREST читается только после проверки `error` — `if (result.error) throw …`, иначе `result.data ?? []`, `result.status` и `.then(({ data }) => …)` — ошибка; запись тоже проверяется: `await supabase.from(…).update(…)` с выброшенным ответом, запрос без `await` или под `void` (построитель ленив — запрос не уходит) и ответ, возвращённый из `async`-функции как есть, — ошибки (`local/no-unchecked-response`, правило смотрит на тип; забытый `await` видит и `no-floating-promises` с `checkThenables`).
- `generateMetadata` читает данные через `server.ts` модуля, как и страница.
- `domain` и `application` возвращают коды, не тексты: ошибка — `code` (у правила ещё `rule`), сообщение Zod — ключ (`NOTE_MESSAGE_KEYS`). Тексты — словарь `ui/messages.ts` модуля с `satisfies Record<ключ | код, string>`; общие коды — `src/shared/ui/form/messages.ts`; язык — `DEFAULT_LOCALE` (`src/shared/domain/locale.ts`).
- Язык внутреннего приложения — next-intl без маршрутизации по языку; сегмент `[locale]` — только для публичного сайта с поиском. При переезде на `[locale]` ссылки переходят на навигацию next-intl, словари не меняются.
- Плановая задача: каждый обработчик в `src/app/api/cron/<задача>/route.ts` (и в группе маршрутов, и в `route.tsx`) объявлен в этом файле (`export function GET(request)` или `export const GET = (request) => {…}`; переэкспорт, деструктуризация и обёртка — ошибка), и первый оператор его тела — `if (!isCronRequest(request)) return new Response(null, { status: 401 })` — `isCronRequest` из `src/shared/lib/cron.ts` сверяет заголовок `Authorization: Bearer …` с секретом `CRON_SECRET` (его присылает Vercel Cron) и отказывает, пока секрет не задан (`local/cron-secret`); расписание — `crons` в `vercel.json`; упавший запуск Vercel Cron сам не повторяет, а на staging (preview-деплой ветки `main`) расписание не выполняется вовсе — задача идемпотентна по периоду и запускается руками или локально. Пишет задача через `createAdminClient()` (сессии пользователя нет; где он разрешён — `security.md`); внутренние пересчёты в базе — `pg_cron`. Открытые префиксы — `PUBLIC_PREFIXES` в `src/proxy.ts`. Долгая или массовая работа — Supabase Queues, когда понадобится. Импорт и экспорт упираются в пределы платформы (размер тела запроса, время функции, число строк в ответе) — таблица пределов и что из них следует — скил `dev-kit:performance-budget`, «Пределы платформы: импорт и экспорт».
- Сценарий, который пишет в таблицы двух модулей одной транзакцией, — функция базы, вызываемая через `rpc` из репозитория владеющего модуля (прямого SQL-подключения и транзакций на стороне приложения нет). Кэш `'use cache'` — только для справочников, одинаковых для всех пользователей; ничего, что выводится из строк пользователя (внутри `'use cache'` нет cookies, а значит нет и RLS).

Подробно: скил `dev-kit:clean-layers`; производительность — `dev-kit:performance-budget`.
