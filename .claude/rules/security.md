# Безопасность данных (Next.js App Router)

- Опорные файлы: `src/shared/lib/safe-action.ts` (`authActionClient`, `actionClient`, `fail`, `handleServerError`), `src/shared/lib/session.ts` (`verifySession`, `requireVerifiedSession`, `verifiedSessionOrResponse`), `src/shared/lib/cron.ts` (`isCronRequest`), `src/shared/infrastructure/env.ts`. Без `import 'server-only'` — только `*.fake.ts`.
- `process.env` читают только `env.ts` и `isProduction` из `src/shared/lib/runtime.ts` (линтер `no-restricted-properties`). Клиенту понадобится `NEXT_PUBLIC_*` — обёртка в `src/shared/lib`; `NODE_ENV` на клиенте допустим.
- Мимо RLS ходит `createAdminClient()` из `src/shared/infrastructure/supabase/admin.ts` (секретный ключ, серверные задачи без сессии): линтер `no-restricted-imports` пускает его только в `src/shared/infrastructure/**` и в файлы `*.admin.ts` инфраструктуры модуля (и по алиасу, и относительным путём); плановая задача в `src/app/api/cron` зовёт `server.ts` модуля, а тот — репозиторий `*.admin.ts`. Свой клиент в обход него тоже закрыт: пакеты `@supabase/supabase-js` и `@supabase/ssr` импортирует только `src/shared/infrastructure` (`local/raw-client`; `import type` можно), а драйвер Postgres и ORM (`postgres`, `pg`, `drizzle-orm`) — никто в `src`, включая `shared/infrastructure` (`local/direct-database`, проба — `tests/lint-rules/fixtures/src/shared/infrastructure/db/index.ts`); динамический `import()` закрыт так же, как обычный импорт: пакеты клиента — `local/raw-client`, `admin` — `local/dynamic-import` (он же требует у `import()` строку-литерал), `session` и `safe-action` — `local/behind-sign-in`, а `env.supabaseSecretKey` вне него не читается (`no-restricted-properties`) — секретный ключ и есть обход RLS, даже через `fetch`. Данные пользователя — всегда через клиент с сессией и явным фильтром по владельцу.
- Сессия: cookie Supabase `httpOnly`, в продакшене `secure`, кроме `localhost` — e2e production-сборки идёт по http, а Safari не хранит `Secure` cookie без https (`src/shared/infrastructure/supabase/cookie-options.ts`); браузерного клиента Supabase нет — `connect-src 'self'` не пускает браузер к Supabase, данные идут через сервер. `src/proxy.ts` передаёт заголовки кэша Supabase (сессия не попадает в CDN) и обновлённые cookies — в пропуске, редиректе и JSON-отказе `/api/*`; без переменных окружения отвечает 503 на непубличные адреса.
- Matcher `src/proxy.ts`: мимо proxy идут только `_next/static/`, `_next/image` и файлы-картинки верхнего уровня (`/logo.png`); всё вложенное — через proxy. Картинки публичных страниц — в корне `public/`; Route Handler, отдающий файл, не полагается на расширение в адресе. Списки путей — `tests/unit/shared/proxy-matcher.test.ts`.
- Route Handler за входом первой строкой зовёт `verifiedSessionOrResponse()` (`src/shared/lib/session.ts`) и возвращает полученный `Response` как есть (`if (session instanceof Response) return session`): без сессии — 401 `{"error":"unauthorized"}`, при незавершённом шаге второго фактора — 403 `{"error":"mfa_required"}` (тела и статусы — `src/shared/lib/api-denial.ts`, те же отдаёт proxy). `requireVerifiedSession()` в Route Handler не годится — он делает редирект. Линтер этого не проверяет — смотрит ревью.
- Неожиданные ошибки — `reportUnexpectedError` (`src/shared/infrastructure/monitoring.ts`): строка JSON в лог и Sentry; Sentry только серверный (`src/instrumentation.ts`): сбор данных запроса выключен целиком (`dataCollection` в `sentryOptions`: адрес посетителя, cookies, заголовки, тела, query, данные запросов к базе), `beforeSend` дополнительно убирает `event.user` и остатки запроса; `tests/unit/shared/instrumentation.test.ts` проверяет исходящий конверт на настоящем `Sentry.init`. Строки `console.*` приложения к событию не прикладываются (`beforeBreadcrumb` убирает крошки `console`; тот же тест) — и всё равно персональных данных и сумм в логах нет: лог читают и в Vercel. Клиентский SDK не ставить — бюджет JS. Ошибки базы и Auth сообщаются только операцией и кодом — `throw databaseError('notes.insert', error)` даёт `notes.insert: 23514`, `authError('auth.signIn', error)` — `auth.signIn: unexpected_failure (500)` (`src/shared/infrastructure/supabase/postgres-errors.ts`, `auth-errors.ts`): без `message`, `details`, `hint` и без `cause` — Postgres цитирует в сообщении введённое значение (`invalid input syntax for type numeric: "…"`), в `details` бывает вся строка с суммами, сообщение Auth может назвать почту, а текст ошибки и её `cause` уходят в лог и в Sentry; в инфраструктуре модуля это держит `local/error-by-code` (в том числе `throw error` самой ошибки провайдера), полный текст — в логах Postgres и Auth проекта Supabase. По той же причине `money()` на нечисловой строке бросает ошибку без самого значения, а брошенное не-`Error` `reportUnexpectedError` отдаёт в Sentry только типом, без полей объекта. Query-строки запросов в Sentry не уходят (`dataCollection.urlQueryParams = false`, иначе исходящие запросы к PostgREST с фильтрами попадают в breadcrumbs).
- Заголовки — в `next.config.ts`. CSP строгий во всех директивах, кроме `script-src 'self' 'unsafe-inline'` и `style-src 'self' 'unsafe-inline'` (инлайн-стили React): App Router вставляет в каждую страницу инлайн-скрипты (тема, загрузчик, данные серверных компонентов), разрешить их без `'unsafe-inline'` может только nonce, а nonce требует рендерить каждую страницу на запрос (`await connection()`) и отказаться от статической оболочки Cache Components; `experimental.sri` инлайн-скрипты не покрывает (проверено в шаблоне). Проект, где все экраны за входом, может выбрать nonce — задача B00-T07: там же, что вместе с nonce обязательно (`instant = false` в корневом layout и замена проверки `<Suspense>`, nonce в `ThemeProvider`, бюджет JS по манифестам). `checkPageQuality` (`tests/e2e/support/page-quality.ts`) сверяет CSP целиком, директиву за директивой (`CONTENT_SECURITY_POLICY`), и отсутствие нарушений в консоли на каждой странице; правка CSP — в `next.config.ts` и в этом списке. `form-action` — с доменом Supabase, если вход через OAuth.
- Без входа открыты только `/`, `/login` и префикс `/api/cron/` (`PUBLIC_PATHS`, `PUBLIC_PREFIXES` в `src/proxy.ts`). Плановую задачу защищает секрет `CRON_SECRET` (задаётся в Vercel, без него — отказ): обработчик и проверка `local/cron-secret` — `.claude/rules/architecture.md`, «Плановая задача». Входящий webhook — свой префикс в `PUBLIC_PREFIXES` вместе с проверкой подписи в обработчике; её линтер не проверяет — смотрит ревью.
- Server Actions за прокси с другим хостом — `serverActions.allowedOrigins`, иначе проверка `Origin` их отклонит.
- Файлы: имя генерирует сервер, путей из запроса нет.
- Периметр Cloudflare Access: либо `proxy.ts` проверяет `Cf-Access-Jwt-Assertion` (jose, JWKS `https://<team>.cloudflareaccess.com/cdn-cgi/access/certs`, `aud` приложения), либо `*.vercel.app` закрыт Deployment Protection — иначе Access обходится по адресу деплоя.
- Зависимости: красный `npm audit --omit=dev --audit-level=high` в CI — обновить пакет, а если исправления нет — временный `overrides` в `package.json` с причиной и датой пересмотра. Мажоры — руками после чтения changelog (Dependabot их пропускает).

Защиты линтера на этой странице ловят ошибку, а не намеренный обход — его ловит ревью кода; как они защищены от отключения и что делать с ложным срабатыванием — `.claude/rules/code-style.md`.

Страница и серверный компонент за входом зовут `requireVerifiedSession()` (линтер этого не проверяет), каждый экспорт файла `'use server'` — цепочка клиента из `safe-action.ts` (`local/server-action`); вход, пароль, второй фактор и перебор — `auth.md`.
