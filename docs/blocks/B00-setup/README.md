## Перед первой задачей

Предусловия и кто их обеспечивает:

- организация GitHub на плане Team (защита веток приватного репозитория) и окружения `staging` и `production` в репозитории (Settings → Environments; ограничение веток у каждого — B00-T01) — админ организации заказчика;
- пустой приватный репозиторий (шаблон переносится без истории, см. B00-T01) и приглашение разработчика с ролью Admin — админ организации; политика Actions организации разрешает сторонние actions по SHA; ключ gitleaks не нужен: проверка «Secrets» запускает программу gitleaks напрямую;
- проекты Supabase staging и production (регион Frankfurt), проект Vercel, организация Sentry в регионе EU — по `docs/release.md`, «Настройка один раз»; на Free-плане Supabase из `config.toml` убирается `[auth.sessions]` (B00-T04).

Разработчик один: он сам читает дифф PR и сливает его; подтверждение выпуска — слияние PR `main → production` в защищённую ветку `production` (кнопки подтверждения у окружения на GitHub Team в приватном репозитории нет). Второй человек для ревью не нужен; чем это закрыто — B00-T01.

Порядок старта: ветка `block/B00-setup` — первой, до правок. Если задачи ведутся в ClickUp — сначала `.claude/rules/clickup.md.example` → `clickup.md` с номером списка, префиксом и тем, кто меняет статусы: без него карточки не завести. Подготовить репозиторий, окружения и дизайн-систему, чтобы первая задача продукта шла сразу по полному циклу: preview-ссылка в PR, зелёный CI, проверка экранов.

## Результат

Репозиторий у заказчика с защищённым `main` и зелёным CI; staging в Vercel и Supabase; дизайн-система заказчика в токенах; тестовый пользователь для проверки экранов; учебный пример шаблона убран.

## Как показать

1. Открыть staging (адрес ветки `main` в Vercel): главная в цветах выбранного стиля, светлая и тёмная тема. Preview-ссылка PR — для разработчика.
2. Войти тестовым пользователем (пароль и код второго фактора) — открывается защищённая главная.
3. В GitHub: `main` защищён, CI зелёный.

## После слияния блока

Staging — это ветка `main`, а PR блока сливается один раз, в конце. Поэтому посреди блока задачи проверяются локально и по preview-ссылке PR, а этот список Claude проходит сразу после слияния, когда обновил `main`:

1. Actions → Deploy database на `main` зелёный целиком: миграции блока (в том числе удаление примера) и настройки Auth из `config.toml` выложены (B00-T03, B00-T04).
2. Вход на адресе staging пользователем, заведённым в панели Supabase staging; при обязательном втором факторе — шаг `/mfa/setup` или `/mfa/verify` (B00-T04).
3. Тестовая ошибка со staging пришла в Sentry с окружением `staging`, без заголовков и cookies (B00-T05).
4. Заголовки staging содержат CSP и остальные заголовки безопасности; с Cloudflare Access — запрос в обход периметра получает отказ (B00-T07).
