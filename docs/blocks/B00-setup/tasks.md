## [ ] B00-T01 Репозиторий и CI

Требования: — · Подзадача: <ссылка>

**Что делаем.** Репозиторий из шаблона в организации заказчика, план GitHub Team у организации (в бесплатной защита веток приватного репозитория недоступна), защита `main` и `production` (PR и зелёный CI; обязательные проверки — `Lint, types, unit, dead code, build`, `Playwright`, `Secrets`, `Semgrep`; `Advisors and pgTAP` обязательной не делать: она запускается только при изменениях базы, и остальные PR зависнут), ветка `production` (`git push origin main:production`), в настройках слияния включены squash и merge commit (выпуск в production — merge commit), удаление веток после слияния (`gh repo edit --delete-branch-on-merge`), оповещения Dependabot, секрет `GITLEAKS_LICENSE` (бесплатный ключ gitleaks для организаций — получает и вносит разработчик, роль Admin достаточно) — в секреты Actions и в Dependabot secrets, иначе проверка «Secrets» на каждом PR Dependabot красная. Создание репозитория: заказчик создаёт пустой приватный репозиторий и приглашает разработчика Admin, разработчик переносит шаблон без истории (руководство по системе разработки, раздел «Проект в организации заказчика», п. 3) — `gh repo create --template` требует доступа заказчика к шаблону. У организации проверить политику Actions (сторонние actions по SHA: `supabase/setup-cli`, `gitleaks-action`, контейнер Semgrep) и назначить required reviewer окружения `production` — заказчик или второй участник, не автор выпуска.
**Результат.** Draft-PR блока открыт до остановки задачи, все проверки CI в нём зелёные.
**Как проверить.** Draft-PR блока (Claude открывает его в этой задаче сам, не дожидаясь `/dev-kit:task-done`; нет правок в файлах — сначала `git commit --allow-empty -m "wip: B00-T01"`): все проверки зелёные, прямой push в `main` запрещён; `gh repo view --json deleteBranchOnMerge` → `true`.

## [ ] B00-T04 Supabase и вход

Требования: — · Подзадача: <ссылка>

**Что делаем.** Проекты staging и production. Способ входа — по требованиям заказчика: email и пароль (от 12 символов, защита от утёкших паролей) или SSO-провайдер, например Google — тогда это задача с кодом и планом (маршрут возврата OAuth, `[auth.external.google]` в `config.toml`, переменные client id/secret, e2e, в CSP `form-action 'self' https://<ref>.supabase.co` — браузер применяет `form-action` и к редиректу после отправки формы входа), не только настройка; в любом случае только по приглашению, саморегистрация выключена. Для финансовых данных — второй фактор (TOTP) и `AUTH_REQUIRE_MFA=true`. Таймаут неактивности сессии: `[auth.sessions]` облако принимает на плане Pro — пока проект на Free, секцию убрать из `config.toml` (строка D-NNN) и вернуть при переходе на Pro. Переключатели, которых нет в `supabase/config.toml` и которые ставятся только в панели Supabase, — руками на staging и production, списком в README блока. `.env.local`; тестовый пользователь — `npm run seed:test-user` по `.env.test.local` (`TEST_USER_EMAIL`, `TEST_USER_PASSWORD`, `TEST_USER_TOTP_SECRET`), код второго фактора — `npm run totp -s`. Вход только через SSO — провайдер Email в production выключить и закрепить в настройках, которые выкладывает `deploy-db.yml`: иначе следующий `config push` вернёт его из `config.toml`. Для этого — секция `[remotes.production]` с `project_id = "<ref production>"` и `[remotes.production.auth.email] enabled = false` в `config.toml` (ref не секрет — он виден в `NEXT_PUBLIC_SUPABASE_URL`; локальные контейнеры именуются по папке, на них это не влияет); проверить на staging до первого выпуска. Секрет Google `SUPABASE_AUTH_EXTERNAL_GOOGLE_SECRET` — в оба окружения GitHub и в `env:` шага «Push Auth and API settings» в `deploy-db.yml`, иначе `config push` падает на `env(…)`. Финансовым — `inactivity_timeout = "30m"` и `jwt_expiry = 900`; отзыв сессии администратором вступает в силу по истечении токена (до 15 минут) — так и записать заказчику. Проверка факторов при ошибке Supabase Auth (бан, отозванная сессия) ведёт на `/login`, не на 500. Окружения GitHub `staging` и `production` с секретами и переменными — по `docs/release.md`, «Настройка один раз», п. 3; перед первой выкладкой — `supabase config diff`, затем Actions → Deploy database → Run workflow на `main`: миграции шаблона пришли раньше секретов и сами на staging не выложились. Проект Supabase на Free засыпает через неделю без запросов: перед показом разбудить в панели, иначе staging и `deploy-db` падают.
**Результат.** Локально и на staging работает вход (со вторым фактором, если он включён) и защищённая страница.
**Как проверить.** `supabase test db` зелёный; Deploy database на `main` зелёный; вход тестовым пользователем с кодом из `npm run totp -s`; регистрация нового пользователя недоступна; при `AUTH_REQUIRE_MFA=true` без второго фактора защищённая страница отправляет на `/mfa/setup` или `/mfa/verify`.

## [ ] B00-T07 Безопасность периметра

Требования: — · Подзадача: <ссылка>

**Что делаем.** CSP шаблона уже строгий во всех директивах, кроме `script-src 'self' 'unsafe-inline'` (`next.config.ts`): App Router вставляет в каждую страницу 9 инлайн-скриптов (тема, загрузчик Turbopack, данные серверных компонентов `__next_f`), которые без nonce не разрешить, а `experimental.sri` покрывает только внешние файлы — проверено в шаблоне (спайк D-075 Finance Hub: с `script-src 'self'` плюс SRI — 9 нарушений и нет гидратации; с nonce в `proxy.ts` на статических страницах Cache Components nonce в разметку не попадает — 22 нарушения). Решение проекта: (а) оставить `'unsafe-inline'` для скриптов — страницы остаются статическими оболочками, защита от XSS ложится на экранирование React, `connect-src 'self'` и `frame-ancestors 'none'`; (б) nonce по руководству Next.js «Content Security Policy»: `proxy.ts` генерирует nonce на запрос и ставит его в заголовок CSP запроса и ответа, `script-src 'self' 'nonce-…' 'strict-dynamic'`, каждая страница рендерится на сервере на запрос (`await connection()` в корневом layout), статическая оболочка и Partial Prerendering не используются — для приложения, где все экраны за входом и зависят от пользователя, потеря невелика, а `'use cache'` для справочников продолжает работать. Для финансовых данных рекомендуется (б). `form-action 'self'` — только при входе паролем (при OAuth браузер применяет его и к редиректу на провайдера). Заголовки безопасности проверены на staging; HSTS с `preload` — когда домен окончательный. Cloudflare Access (проверка его JWT в `src/proxy.ts`, закрытый `*.vercel.app`) — когда домен заведён на Cloudflare; нет домена — отдельной задачей после B00, здесь только заголовки.
**Результат.** Выбранный вариант записан строкой D-NNN; браузер выполняет только скрипты приложения (при (б) — только с nonce); с Access — без входа через периметр приложение недоступно.
**Как проверить.** `tests/e2e/ui-quality.spec.ts` на каждой странице не видит в консоли ни одного нарушения CSP (при (б) — обновить ожидаемый заголовок в тесте); заголовки staging (`curl -sI <адрес>`) содержат CSP и остальные заголовки безопасности; при (б) `npm run build` показывает все маршруты динамическими (`ƒ`), а `npm run perf` остаётся в бюджете; с Access — запрос к staging в обход периметра получает отказ.
