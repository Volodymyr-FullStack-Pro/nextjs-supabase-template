## [ ] B00-T03 Supabase и вход

Требования: — · Подзадача: <ссылка>

**Что делаем.** Проекты staging и production. Способ входа — по требованиям заказчика: email и пароль (от 12 символов, защита от утёкших паролей) или SSO-провайдер, например Google; в любом случае только по приглашению, саморегистрация выключена. Для финансовых данных — второй фактор (TOTP) и `AUTH_REQUIRE_MFA=true`. Таймаут неактивности сессии. Переключатели, которых нет в `supabase/config.toml` и которые ставятся только в панели Supabase, — руками на staging и production, списком в README блока. `.env.local`, первая миграция, тестовый пользователь (Studio → Authentication) с данными в `.env.test.local` (`TEST_USER_EMAIL`, `TEST_USER_PASSWORD`). Вход только через SSO — провайдер Email в production выключить и закрепить в настройках, которые выкладывает `deploy-db.yml`: иначе следующий `config push` вернёт его из `config.toml` (переопределение для среды production; проверить на staging до первого выпуска). Финансовым — `inactivity_timeout = "30m"` и `jwt_expiry = 900`. Окружения GitHub `staging` и `production` с секретами и переменными — по `docs/release.md`, «Настройка один раз», п. 3; перед первой выкладкой — `supabase config diff`, затем Actions → Deploy database → Run workflow на `main`: миграции шаблона пришли раньше секретов и сами на staging не выложились.
**Результат.** Локально и на staging работает вход (со вторым фактором, если он включён) и защищённая страница.
**Как проверить.** `supabase test db` зелёный; Deploy database на `main` зелёный; вход тестовым пользователем; регистрация нового пользователя недоступна; при `AUTH_REQUIRE_MFA=true` без второго фактора защищённая страница отправляет на `/mfa/setup` или `/mfa/verify`.

## [ ] B00-T06 Безопасность периметра

Требования: — · Подзадача: <ссылка>

**Что делаем.** Строгий CSP без nonce (nonce делает все страницы динамическими): хэши скриптов через Subresource Integrity (`experimental.sri: { algorithm: 'sha256' }` в `next.config.ts`, функция экспериментальная) и `script-src 'self'` (в dev — плюс `'unsafe-eval'`), а также `default-src 'self'`, `img-src 'self' blob: data:`, `font-src 'self'`, `object-src 'none'`, `base-uri 'none'`, `form-action 'self'` (и домен Supabase при входе через OAuth), `frame-ancestors 'none'`, `upgrade-insecure-requests` — по руководству Next.js «Content Security Policy». Если приложение закрыто Cloudflare Access — проверка его JWT в `src/proxy.ts` или закрытый `*.vercel.app`; заголовки безопасности проверены на staging.
**Результат.** Без входа через периметр приложение недоступно; браузер выполняет только скрипты приложения.
**Как проверить.** e2e проходит страницы и не видит в консоли ни одного нарушения CSP; заголовки staging (`curl -sI <адрес>`) содержат CSP и остальные заголовки безопасности; запрос к staging в обход периметра получает отказ.
