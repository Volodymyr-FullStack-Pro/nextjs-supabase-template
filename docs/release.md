# Выпуск

Путь кода: локально → preview на каждый PR → staging → production. Production выпускает человек.

## Среды

| Среда      | Код                | База                | Для чего                             |
| ---------- | ------------------ | ------------------- | ------------------------------------ |
| Локально   | `npm run dev`      | `supabase start`    | разработка, тесты                    |
| Preview    | каждый PR (Vercel) | Supabase staging    | проверка разработчиком               |
| Staging    | ветка `main`       | Supabase staging    | проверка перед выпуском              |
| Production | ветка `production` | Supabase production | пользователи, только реальные данные |

Preview — для разработчика; заказчику показывается staging после слияния блока. Preview работает с базой staging, а миграции попадают туда только после слияния в `main`: задачу с новой миграцией по ссылке preview не показать до слияния блока — её проверяют локально.

Приложение и база — в одном регионе: функции Vercel во Франкфурте (`fra1` в `vercel.json`), проекты Supabase — в регионе Frankfurt (eu-central-1). Регион проекта Supabase выбирается при создании и потом не меняется.

## Настройка один раз

1. **Supabase.** Два проекта, staging и production, в регионе Frankfurt; в production включить PITR. Проект на плане Free засыпает через неделю без запросов: перед показом разбудить в панели (Restore project), иначе staging не открывается и `deploy-db` падает; перевод на Pro — при подготовке к запуску. В каждом: Authentication → Sign In / Providers → «Allow new users to sign up» = off. Только в облаке, через панель (в `config.toml` этой настройки нет): защита от утёкших паролей (Authentication → Providers → Email → «Prevent use of leaked passwords», тариф Pro и выше). Второй фактор (TOTP) из `config.toml` работает на всех тарифах; в production без переменной `AUTH_REQUIRE_MFA` он обязателен для всех (выключается только явным `AUTH_REQUIRE_MFA=false` — для проектов без финансовых данных), финансовые проекты ставят `AUTH_REQUIRE_MFA=true` и в Preview; один фактор на пользователя (`max_enrolled_factors = 1`), пока нет экрана факторов. Ограничения сессий из `config.toml` (`[auth.sessions]`: 24 ч всего, 8 ч без активности; финансовым проектам — `inactivity_timeout = "30m"` и `jwt_expiry = 900`: бездействие проверяется только при обновлении токена, фактический срок — таймаут плюс срок токена) облако принимает на тарифе Pro и выше: на Free секцию `[auth.sessions]` убрать, иначе `config push` откажет.
2. **Vercel.** Settings → Environments → Production → Branch Tracking — ветка `production`; домен staging назначить на ветку `main`; переменные окружения — отдельно для Preview и Production (`.env.example`): `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `AUTH_REQUIRE_MFA`, `SENTRY_*`, `CRON_SECRET` при плановых задачах; `SUPABASE_SECRET_KEY` — только если в проекте есть серверные задачи без сессии пользователя (`createAdminClient()`), как server-only переменная. `DATABASE_URL` и `DATABASE_CA_CERT` на Vercel не задаются: порт базы закрыт сетевыми ограничениями (они действуют и на пулер Supavisor), приложение работает с базой только через HTTPS API Supabase, а `db()` (Drizzle) — локально и в CI. Если проект осознанно открывает пулер для Vercel (нужны Static IPs) — `DATABASE_URL` пула в режиме transaction, порт 6543, и `DATABASE_CA_CERT` (Project Settings → Database → SSL): подключение идёт по TLS с проверкой сертификата (`verify-full`). Регион функций берётся из `vercel.json`. Vercel Cron выполняется только в production: на staging плановую задачу запускают руками (Run) или проверяют локально. Vercel Toolbar на preview-деплоях вставляет скрипт с `vercel.live`, который CSP шаблона блокирует (нарушения в консоли preview): выключить Toolbar в настройках проекта Vercel или разрешать `https://vercel.live` в `script-src` и `connect-src` только при `VERCEL_ENV=preview`.
3. **GitHub.** Ветка `production` — `git push origin main:production`. Защитить `main` и `production` (только PR, зелёный CI); в настройках слияния оставить squash и merge commit. Два окружения (Settings → Environments): `staging` и `production`, у `production` — обязательное подтверждение (required reviewers). В каждом — секреты `SUPABASE_ACCESS_TOKEN` (Supabase → Account → Access Tokens), `SUPABASE_DB_PASSWORD`, `SUPABASE_PROJECT_REF` и переменная `SITE_URL` (адрес приложения в этой среде, `https://…`). Пока секретов нет, выкладка базы пропускается с предупреждением; когда они заданы — первая выкладка вручную: Actions → Deploy database → Run workflow на `main`. `GITLEAKS_LICENSE` — в секреты Actions и в Dependabot secrets (Settings → Secrets and variables → Dependabot): workflow от PR Dependabot видит только их, иначе обязательная проверка «Secrets» красная на каждом его PR. `SUPABASE_ACCESS_TOKEN` — личный токен участника: при передаче проекта заказчик выпускает свой и меняет секрет в обоих окружениях. Вход через Google (`[auth.external.google]` с `env(SUPABASE_AUTH_EXTERNAL_GOOGLE_SECRET)`) — секрет `SUPABASE_AUTH_EXTERNAL_GOOGLE_SECRET` в оба окружения и в `env:` шага «Push Auth and API settings» в `deploy-db.yml`, иначе `config push` падает. Переопределения `[remotes.production]` в `config.toml` работают только с указанным в них `project_id`; ref проекта не секрет (он виден в `NEXT_PUBLIC_SUPABASE_URL` любого браузера) — его коммитят.
   Порт Postgres закрыт сетевыми ограничениями (Database → Network Restrictions, приложение ходит только через HTTPS API)? Переменная окружения `SUPABASE_NETWORK_RESTRICTED=true`: `deploy-db.yml` на время `link` и `db push` добавляет IP раннера (`/32`), а после — даже если выкладка упала — возвращает сохранённый список целиком.
   Токен `SUPABASE_ACCESS_TOKEN` тогда должен иметь право менять сетевые ограничения проекта (роль Owner или Administrator в организации Supabase); `[db.network_restrictions]` в `config.toml` оставить `enabled = false`, иначе `config push` перепишет список.
4. **Sentry** — до первого выпуска в production. Организацию создавать в регионе данных EU: регион выбирается при создании организации и потом не меняется, а ошибки несут адреса страниц и технические данные пользователей из ЕС. В Vercel: `SENTRY_DSN`, для staging ещё `SENTRY_ENVIRONMENT=staging`; для читаемого стека — `SENTRY_AUTH_TOKEN`, `SENTRY_ORG`, `SENTRY_PROJECT` (source maps уходят при сборке; без них сборка тоже проходит). Подключён только серверный SDK (`src/instrumentation.ts`): ошибки серверных компонентов, Route Handlers, `proxy.ts` и неожиданные ошибки Server Actions. Клиентского SDK нет: он добавил бы десятки килобайт JS на каждую страницу и вывел бы маршруты за бюджет (`npm run budget`); ошибки в браузере ловят `error.tsx` и `global-error.tsx`. Персональные данные не уходят: `beforeSend` убирает заголовки, cookies и тело запроса. Неудачные входы и неверные коды второго фактора пишутся в лог строкой `auth-failure`; в Sentry уходит событие `auth-failure` (тег `code`), когда Supabase Auth ответил лимитом (`too-many-attempts`, `too-many-totp-attempts`) — в Sentry → Alerts завести правило «событие `auth-failure` за 5 минут» и читать логи Vercel за тот же период.
5. **Логи** — одна строка JSON на событие (`{ type, …, durationMs }`) через `console.info` / `console.error`, без персональных данных, сумм и токенов: так их читают Vercel и поиск по логам. Ожидаемые ошибки (правило домена, неверный ввод) в лог не пишутся; неожиданная ошибка Server Action — строка `{ "type": "action-error", "error", "message" }` и событие в Sentry (`src/shared/lib/safe-action.ts`).

## Миграции

1. Локально: `supabase migration new <имя>` → SQL (в начале — `set lock_timeout` и `set statement_timeout`) → `supabase test db` → `npm run db:check-migrations` → `npm run db:types` → PR (CI `db.yml` проверяет неизменность слитых миграций, advisors, `db lint`, pgTAP, Squawk и что типы совпадают с миграциями).
2. Слияние в `main` → workflow `deploy-db.yml` сам выкладывает на staging: `supabase link`, `supabase db push --remote`, `supabase config push` (настройки Auth и API из `config.toml`; `site_url` и адреса возврата подменяются переменной `SITE_URL`). Проверить staging.
3. Перед первым включением выкладки посмотреть, что `config push` поменяет в облаке: `supabase link --project-ref <staging>` и `supabase config diff` (CLI 3 подставляет в настройки переменные `SUPABASE_*` из окружения и `.env`-файлов — diff показывает и их).
4. Миграцию, уже слитую в `main`, не правят и не удаляют — исправление новой миграцией (`db.yml` проверяет это на каждом PR). Миграция только добавляет (новые колонки и таблицы), удаление — отдельным выпуском, когда код старое уже не читает: при выпуске база выходит после кода (её выкладка ждёт подтверждения), поэтому новый код должен работать и со старой схемой; иначе миграция — отдельным выпуском раньше кода.

## Выпуск в production

PR `main → production` сливается merge commit, не squash (иначе `production` расходится с `main` и следующий выпуск конфликтует), с описанием «что выходит» (блоки, требования), CI зелёный → слияние человеком → Vercel деплоит код, а `deploy-db.yml` ждёт подтверждения в окружении `production` и выкладывает миграции и настройки Auth. Упавшую выкладку повторить: Actions → Deploy database → Run workflow на ветке `production`.

## Если что-то упало

- **Красный `deploy-db` на staging** (push в `main`): открыть лог шага в Actions; миграцию не править — исправление новой миграцией вперёд (`npm run db:check-migrations`, `supabase test db`), PR, слияние, выкладка пойдёт сама; повторить вручную — Actions → Deploy database → Run workflow. Пока не исправлено, код на staging новее базы — проверить, что приложение терпит старую схему (миграции только добавляют).
- **Красный `deploy-db` на production:** ничего не повторять вслепую; сравнить `supabase migration list --remote` с репозиторием, причину — в `decisions.md`, исправление — новой миграцией через staging.
- **Оповещение Sentry:** читает разработчик (Sentry → Issues, окружение в тэге); ошибка воспроизводится локально тестом первым, правка — обычной задачей `fix/<имя>`; серия неверных кодов второго фактора или входов — признак подбора: заблокировать пользователя в Supabase → Authentication и сообщить заказчику.
- **Staging не отвечает:** проект Supabase на Free уснул — Restore project в панели.
- **Пользователь потерял аутентификатор:** фактор один на пользователя (`max_enrolled_factors = 1`), сам он новый не подключит; администратор удаляет фактор в Supabase → Authentication → Users → пользователь → Factors (или `auth.admin.mfa.deleteFactor`), после чего вход ведёт на `/mfa/setup`. Личность подтверждать голосом или лично, не по почте.

## Откат

- Код — Vercel Instant Rollback на предыдущий деплой.
- База — новая миграция, исправляющая вперёд; авария с данными — восстановление PITR (план Pro; пока проект на Free, откат только миграцией вперёд — реальных данных на Free быть не должно).
- Причина и вывод — строка D-NNN в `docs/knowledge/decisions.md`.

`ADDITIONAL_REDIRECT_URLS` (переменная окружения GitHub, необязательно) — адреса возврата после входа через `config push`, через запятую; для staging добавьте маску адресов preview Vercel (например `https://*-<команда>.vercel.app/**`), иначе вход через SSO на preview вернёт на staging. Без неё — только `SITE_URL`.
