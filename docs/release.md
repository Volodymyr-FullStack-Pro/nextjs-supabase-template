# Выпуск

Путь кода: локально → preview на каждый PR → staging → production. Production выпускает человек.

## Среды

| Среда      | Код                | База                | Для чего                             |
| ---------- | ------------------ | ------------------- | ------------------------------------ |
| Локально   | `npm run dev`      | `supabase start`    | разработка, тесты                    |
| Preview    | каждый PR (Vercel) | Supabase staging    | проверка разработчиком               |
| Staging    | ветка `main`       | Supabase staging    | проверка перед выпуском              |
| Production | ветка `production` | Supabase production | пользователи, только реальные данные |

Preview — для разработчика; заказчику показывается staging после слияния блока. Preview работает с базой staging, а миграции попадают туда только после слияния в `main`: задачу с новой миграцией по ссылке preview не показать до слияния блока — её проверяют локально. Staging — это ветка `main`: пока PR блока не слит, на staging прежний код и прежняя база. Поэтому посреди блока код, заголовки и настройки Vercel проверяют по preview-ссылке PR, а то, что видно только на staging (выкладка базы из `main`, вход на адресе staging), — после слияния блока.

Приложение и база — в одном регионе: функции Vercel во Франкфурте (`fra1` в `vercel.json`), проекты Supabase — в регионе Frankfurt (eu-central-1). Регион проекта Supabase выбирается при создании и потом не меняется.

## Настройка один раз

1. **Supabase.** Два проекта, staging и production, в регионе Frankfurt; в production включить PITR. Проект на плане Free засыпает через неделю без запросов: перед показом разбудить в панели (Restore project), иначе staging не открывается и `deploy-db` падает; перевод на Pro — при подготовке к запуску. В каждом: Authentication → Sign In / Providers → «Allow new users to sign up» = off. Ключ подписи JWT — асимметричный: `curl https://<ref>.supabase.co/auth/v1/.well-known/jwks.json` показывает ключ с `"alg":"ES256"` (у новых проектов так по умолчанию). С ключом HS256 каждая проверка сессии `getClaims()` в `proxy.ts` и `session.ts` становится запросом к Supabase Auth вместо локальной проверки подписи — перевести проект на асимметричный ключ в панели (JWT Signing Keys). Только в облаке, через панель (в `config.toml` этой настройки нет): защита от утёкших паролей (Authentication → Providers → Email → «Prevent use of leaked passwords», тариф Pro и выше). Второй фактор (TOTP) из `config.toml` работает на всех тарифах; в production без переменной `AUTH_REQUIRE_MFA` он обязателен для всех (выключается только явным `AUTH_REQUIRE_MFA=false` — для проектов без финансовых данных), финансовые проекты ставят `AUTH_REQUIRE_MFA=true` и в Preview; один фактор на пользователя (`max_enrolled_factors = 1`), пока нет экрана факторов. Ограничения сессий из `config.toml` (`[auth.sessions]`: 24 ч всего, 8 ч без активности; финансовым проектам — `inactivity_timeout = "30m"` и `jwt_expiry = 900`: бездействие проверяется только при обновлении токена, фактический срок — таймаут плюс срок токена) облако принимает на тарифе Pro и выше: на Free секцию `[auth.sessions]` убрать, иначе `config push` откажет.
2. **Vercel.** Settings → Environments → Production → Branch Tracking — ветка `production`; домен staging назначить на ветку `main`; переменные окружения — отдельно для Preview и Production (`.env.example`): `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `AUTH_REQUIRE_MFA`, `SENTRY_*`, `CRON_SECRET` — с первой плановой задачей (случайная строка от 32 символов; Vercel Cron сам шлёт `Authorization: Bearer $CRON_SECRET`, без переменной `/api/cron/*` отвечает отказом); `SUPABASE_SECRET_KEY` — только если в проекте есть серверные задачи без сессии пользователя (`createAdminClient()`), как server-only переменная. Адрес базы на Vercel не задаётся: порт Postgres закрыт сетевыми ограничениями (они действуют и на пулер Supavisor), приложение работает с базой только через HTTPS API Supabase (`.claude/rules/db.md`). Регион функций берётся из `vercel.json`. `.npmrc` проекта действует и на сборке: в логе первой сборки проверить, что npm не ниже 11.19 — на более старом запрет install-скриптов зависимостей не действует (README, «Зависимости и lock-файл»). Vercel Cron выполняется только в production: на staging плановую задачу запускают руками (Run) или проверяют локально. Vercel Toolbar на preview-деплоях вставляет скрипт с `vercel.live`, который CSP шаблона блокирует (нарушения в консоли preview): выключить Toolbar в настройках проекта Vercel или разрешать `https://vercel.live` в `script-src` и `connect-src` только при `VERCEL_ENV=preview`.
3. **GitHub.** Ветка `production` — `git push origin main:production`. Защитить `main` и `production`: только PR, зелёный CI, запрет удаления ветки и force-push (иначе разрешённая Claude команда удаления слитых веток может снести и их); в настройках слияния оставить squash и merge commit, rebase выключить: выпуск `main → production` — только merge commit, а rebase, как и squash, развёл бы `production` и `main`. Разработчик один, поэтому обязательных одобрений PR — 0: он сам читает дифф перед слиянием. Workflow видит секреты окружений, и правку `.github/workflows/*` хук плагина `dev-kit` пропускает только с подтверждением человека. `CODEOWNERS` с обязательным ревью `.github/**` — включить, когда появится второй разработчик.
   Два окружения (Settings → Environments): `staging` и `production`. У каждого — Deployment branches and tags → Selected branches and tags: `staging` — только `main`, `production` — только `production`; без этого workflow с любой ветки может назвать `environment: staging` и получить его секреты. Подтверждения выпуска кнопкой окружения нет: на плане Team в приватном репозитории окружения, их секреты и ограничение веток есть, а required reviewers и таймер ожидания — только в публичном репозитории или на Enterprise. Подтверждение выпуска — слияние PR `main → production` в защищённую ветку `production`, а окружение `production` принимает только эту ветку. Станет репозиторий публичным или организация перейдёт на Enterprise — у `production` можно добавить required reviewers.
   Минуты Actions: Team включает $18 в месяц на вычисления Actions (около 3000 минут Linux-раннера); CI идёт на каждый push в ветку открытого PR и в `main`, замер скорости и проверка генератора — только в контрольных точках (push в `main`, PR не в черновике, раз в неделю). Расход — `npm run ci:usage` (README, «Команды»); бюджет Actions с остановкой — у владельца организации: Settings → Billing and licensing → Budgets and alerts, бюджет не удалять — без него расход не ограничен.
   Команды настройки — с ролью Admin на репозиторий; защита веток — файл `docs/ops/github/branch-protection.json`. Текст коммита squash-слияния — заголовок и описание PR (`squash_merge_commit_message=PR_BODY`), а не тексты коммитов ветки: иначе `[skip ci]` из коммита `handoff:` попадает в коммит слияния, и GitHub не запускает в `main` ни CI, ни выкладку миграций:

   ```bash
   R=repos/<org>/<repo>
   gh repo edit <org>/<repo> --delete-branch-on-merge --enable-rebase-merge=false --enable-squash-merge --enable-merge-commit
   gh api -X PATCH $R -f squash_merge_commit_title=PR_TITLE -f squash_merge_commit_message=PR_BODY
   gh api -X PUT $R/vulnerability-alerts
   gh api -X PUT $R/automated-security-fixes
   git push origin main:production
   for E in staging production; do
     echo '{"deployment_branch_policy":{"protected_branches":false,"custom_branch_policies":true}}' | gh api -X PUT $R/environments/$E --input -
   done
   gh api -X POST $R/environments/staging/deployment-branch-policies -f name=main -f type=branch
   gh api -X POST $R/environments/production/deployment-branch-policies -f name=production -f type=branch
   for B in main production; do gh api -X PUT $R/branches/$B/protection --input docs/ops/github/branch-protection.json; done
   ```

   В `branch-protection.json`: `enforce_admins: true` — правила действуют и на администратора; `required_approving_review_count: 0` — разработчик один; `app_id: 15368` — зелёный статус засчитывается только от GitHub Actions. Проверить: Settings → Branches и Settings → Environments.
   В каждом окружении — секреты `SUPABASE_ACCESS_TOKEN`, `SUPABASE_DB_PASSWORD`, `SUPABASE_PROJECT_REF` и переменная `SITE_URL` (адрес приложения в этой среде, `https://…`). `SUPABASE_ACCESS_TOKEN` — свой у каждого окружения: токен с областью «один проект» и только с правами, которые нужны `deploy-db.yml` (привязка проекта, настройки Auth и API, сетевые ограничения; миграции идут по паролю базы), а не один личный токен на всё — личный токен несёт права всей учётной записи, и из `staging` с ним открыт production. На машине разработчика `supabase login` — токеном staging; токена production на ней нет. При передаче проекта заказчик выпускает свои токены и меняет секреты в обоих окружениях.
   Пока секретов нет, выкладка базы пропускается с предупреждением; когда они заданы — первая выкладка вручную: Actions → Deploy database → Run workflow на `main`. Ключ gitleaks и секрет для него не нужны: проверка «Secrets» запускает программу gitleaks напрямую (`ci.yml`). Вход через Google (`[auth.external.google]` с `env(SUPABASE_AUTH_EXTERNAL_GOOGLE_SECRET)`) — секрет `SUPABASE_AUTH_EXTERNAL_GOOGLE_SECRET` в оба окружения и в `env:` шага «Push Auth and API settings» в `deploy-db.yml`, иначе `config push` падает. Переопределения `[remotes.production]` в `config.toml` работают только с указанным в них `project_id`; ref проекта не секрет (он виден в `NEXT_PUBLIC_SUPABASE_URL` любого браузера) — его коммитят.
   Порт Postgres закрыт сетевыми ограничениями (Database → Network Restrictions, приложение ходит только через HTTPS API)? Две переменные окружения: `SUPABASE_NETWORK_RESTRICTED=true` и `SUPABASE_DB_ALLOWED_CIDRS` — эталонный список адресов, которым открыт порт базы (CIDR с маской через запятую, как показывает панель; пусто — «Restrict all access»). `deploy-db.yml` сверяет список проекта с эталоном и при расхождении останавливается; на время `link` и `db push` добавляет IP раннера (`/32`, адрес подтверждают два независимых сервиса), а после — даже если выкладка упала — ставит ровно эталон.
   Токен `SUPABASE_ACCESS_TOKEN` тогда должен иметь право менять сетевые ограничения проекта (у личного токена — роль Owner или Administrator в организации Supabase); `[db.network_restrictions]` в `config.toml` оставить `enabled = false`, иначе `config push` перепишет список.

4. **Sentry** — до первого выпуска в production. Организацию создавать в регионе данных EU: регион выбирается при создании организации и потом не меняется, а ошибки несут адреса страниц и технические данные пользователей из ЕС. В Vercel: `SENTRY_DSN`, для staging ещё `SENTRY_ENVIRONMENT=staging`; для читаемого стека — `SENTRY_AUTH_TOKEN`, `SENTRY_ORG`, `SENTRY_PROJECT` (source maps уходят при сборке; без них сборка тоже проходит). Подключён только серверный SDK (`src/instrumentation.ts`): ошибки серверных компонентов, Route Handlers, `proxy.ts` и неожиданные ошибки Server Actions. Клиентского SDK нет: он добавил бы десятки килобайт JS на каждую страницу и вывел бы маршруты за бюджет (`npm run budget`); ошибки в браузере ловят `error.tsx` и `global-error.tsx`. Адрес посетителя, cookies, заголовки, тела и query-строки запросов SDK не собирает (`dataCollection` в `src/instrumentation.ts`), `beforeSend` дополнительно убирает `event.user` и остатки запроса; в событии остаются метод, путь, текст ошибки, стек и строки `console.*` приложения — поэтому правило «в логах нет персональных данных и сумм» действует и для Sentry. Неудачные входы и неверные коды второго фактора пишутся в лог строкой `auth-failure`; в Sentry уходит событие `auth-failure` (тег `code`), когда Supabase Auth ответил лимитом (`too-many-attempts`, `too-many-totp-attempts`) — в Sentry → Alerts завести правило «событие `auth-failure` за 5 минут» и читать логи Vercel за тот же период.
5. **Логи** — одна строка JSON на событие (`{ type, …, durationMs }`) через `console.info` / `console.error`, без персональных данных, сумм и токенов: так их читают Vercel и поиск по логам. Ожидаемые ошибки (правило домена, неверный ввод) в лог не пишутся; неожиданная ошибка Server Action — строка `{ "type": "action-error", "error", "message" }` и событие в Sentry (`src/shared/lib/safe-action.ts`); действие дольше секунды — строка `{ "type": "slow-action", "durationMs" }` (там же, порог `SLOW_ACTION_MS`): имени действия в ней нет, его видно по запросу в логах Vercel.

## Миграции

1. Локально: `npm run db:new <имя>` (файл сразу с `set lock_timeout` и `set statement_timeout`; голый `supabase migration new` в оболочке Claude Code ждёт ввод и зависает) → SQL → `supabase migration up` → `npm run db:types` → `npm run gate` (в нём pgTAP, advisors, `db lint`, Squawk и e2e) → PR (CI `db.yml` проверяет неизменность слитых миграций, advisors, `db lint`, pgTAP, Squawk и что типы совпадают с миграциями).
2. Слияние в `main` → workflow `deploy-db.yml` сам выкладывает на staging: `supabase link`, `supabase db push --remote`, `supabase config push` (настройки Auth и API из `config.toml`; `site_url` и адреса возврата подменяются переменной `SITE_URL`). Проверить staging.
3. Перед первым включением выкладки посмотреть, что `config push` поменяет в облаке: `supabase link --project-ref <staging>` и `supabase config diff` (CLI 3 подставляет в настройки переменные `SUPABASE_*` из окружения и `.env`-файлов — diff показывает и их).
4. Миграцию, уже слитую в `main`, не правят и не удаляют — исправление новой миграцией (`db.yml` проверяет это на каждом PR). Миграция только добавляет (новые колонки и таблицы), удаление — отдельным выпуском, когда код старое уже не читает: при выпуске база выходит после кода (её выкладка ждёт подтверждения), поэтому новый код должен работать и со старой схемой; иначе миграция — отдельным выпуском раньше кода.

## Выпуск в production

PR `main → production` сливается merge commit, не squash (иначе `production` расходится с `main` и следующий выпуск конфликтует), с описанием «что выходит» (блоки, требования), CI зелёный (в нём e2e и замер скорости страниц на объёме данных — `npm run perf`, пороги в `tests/perf/pages.ts`) → слияние разработчиком — оно и есть подтверждение выпуска (кнопки подтверждения у окружения на Team нет) → Vercel деплоит код, а `deploy-db.yml` в окружении `production`, которое принимает только ветку `production`, выкладывает миграции и настройки Auth. Упавшую выкладку повторить: Actions → Deploy database → Run workflow на ветке `production`.

## Если что-то упало

- **Красный `deploy-db` на staging** (push в `main`): открыть лог шага в Actions; миграцию не править — исправление новой миграцией вперёд (`npm run db:check-migrations`, `supabase test db`), PR, слияние, выкладка пойдёт сама; повторить вручную — Actions → Deploy database → Run workflow. Пока не исправлено, код на staging новее базы — проверить, что приложение терпит старую схему (миграции только добавляют).
- **`deploy-db` остановился на шаге «Open the database port for this runner»:** список Database → Network Restrictions не совпал с `SUPABASE_DB_ALLOWED_CIDRS` — чаще всего остался адрес раннера после оборванной выкладки. Оба списка — в логе шага. Убрать лишний адрес в панели (или обновить переменную, если список меняли осознанно) и повторить запуск. Вторая причина — `SUPABASE_NETWORK_RESTRICTED=true`, а ограничения в проекте не применены и список пуст (порт открыт всем): применить эталон в панели и повторить; если порт должен быть открыт — снять переменную.
- **Красный `deploy-db` на production:** ничего не повторять вслепую; сравнить `supabase migration list --remote` с репозиторием, причину — в `decisions.md`, исправление — новой миграцией через staging.
- **Оповещение Sentry:** читает разработчик (Sentry → Issues, окружение в тэге); ошибка воспроизводится локально тестом первым, правка — обычной задачей `fix/<имя>`; серия неверных кодов второго фактора или входов — признак подбора: заблокировать пользователя в Supabase → Authentication и сообщить заказчику.
- **Staging не отвечает:** проект Supabase на Free уснул — Restore project в панели.
- **Красная проверка «Secrets»:** gitleaks проверяет историю всех веток репозитория (`fetch-depth: 0`, у gitleaks — `git log --all`), поэтому находка в любой ветке, даже не в этом PR, красит каждый PR: утечка в любой ветке — всё равно утечка. Ветка находки — `git branch -a --contains <коммит из лога>`. Настоящий секрет — отозвать и выпустить новый, ветку с ним удалить. Ложную находку в старом коммите снимает только строка в `.gitleaksignore` с её отпечатком (fingerprint из лога). Правило по значению в `.gitleaks.toml` (`regexes`, `stopwords`) тоже снимет находку, но спрячет то же значение и в новых коммитах — отпечаток точнее.
- **Пользователь потерял аутентификатор:** фактор один на пользователя (`max_enrolled_factors = 1`), сам он новый не подключит; администратор удаляет фактор в Supabase → Authentication → Users → пользователь → Factors (или `auth.admin.mfa.deleteFactor`), после чего вход ведёт на `/mfa/setup`. Личность подтверждать голосом или лично, не по почте.

## Откат

- Код — Vercel Instant Rollback на предыдущий деплой.
- База — новая миграция, исправляющая вперёд; авария с данными — восстановление PITR (план Pro; пока проект на Free, откат только миграцией вперёд — реальных данных на Free быть не должно).
- Причина и вывод — строка D-NNN в `docs/knowledge/decisions.md`.

`ADDITIONAL_REDIRECT_URLS` (переменная окружения GitHub, необязательно) — адреса возврата после входа через `config push`, через запятую; для staging добавьте маску адресов preview Vercel (например `https://*-<команда>.vercel.app/**`), иначе вход через SSO на preview вернёт на staging. Без неё — только `SITE_URL`.
